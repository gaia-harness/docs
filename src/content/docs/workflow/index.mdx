GAIA's rules, skills, and guardrails are in place from the start of every session, so they apply to every ordinary request. You never call them yourself.

At session start they take [less than 1%](/models-and-context/token-efficiency/) of a 1M-token window.

## Mostly, you just prompt as usual

Working in GAIA is the same as working with any coding agent: you describe what you want, and it does the work. Claude reaches for GAIA's [skills](/skills/) on its own, based on what you ask for.

Ask for a component, a fix, a refactor:

```
> Add a date-range filter to the saved-search panel.
```

Notice that this prompt did not ask for a test. But GAIA enforces [test-driven development (TDD)](/workflow/tdd/), so Claude writes a failing test first, then the code that makes it pass. A separate reviewer [checks that each test is worth keeping](/workflow/tdd/#the-worthiness-review). TDD happens without you asking, so you know every test works and earns its place.

## Every task follows one lifecycle

Every task, with or without a command, goes through the same [steps](/workflow/work-lifecycle/). GAIA [isolates](/workflow/work-lifecycle/#isolation-policy) the work so tasks running at the same time never overwrite each other's changes. It commits through the [Quality Gate](/workflow/code-audit-team/#quality-gate), opens a draft pull request, has the [Code Audit Team](/workflow/code-audit-team/) audit it, then merges and cleans up.

The exception is an edit you say you will review or commit yourself: Claude leaves it uncommitted and skips all of this.

## When to reach for a command

The `/gaia-*` commands are for specific moments, not everyday driving:

| When you're... | Reach for | Why |
| --- | --- | --- |
| Starting a feature whose shape isn't settled | [`/gaia-spec`](/workflow/spec/) | Pins down intent and acceptance tests, saves a SPEC, and plans it in the same session. |
| Turning a big feature into parallel work | [`/gaia-plan`](/workflow/plan/) | Splits it into phases, defines the shared types and interfaces the phases build on, and writes a kickoff prompt you paste to start the work. |
| Tech-debt issues have piled up | [`/gaia-debt`](/workflow/debt/) | Fixes the backlog, highest severity first, through the audit gate. |

Small, clear changes do not need a spec or a plan. When your request would benefit from one, GAIA [recommends](/workflow/work-lifecycle/#spec-plan-or-just-do-it) it, even if you didn't name a command.

## A feature, start to finish

1. **Define what to build.** Run `/gaia-spec add saved-search filters`. It asks a few questions, confirms the intent and the acceptance tests in plain language, and saves a SPEC. Then it plans the SPEC in the same session and ends with a kickoff prompt.
2. **Build it.** Run `/clear` and paste the kickoff prompt. GAIA turns the SPEC's acceptance tests into failing [Playwright](https://playwright.dev/) tests, builds each phase, commits it through the Quality Gate, and opens a draft pull request.
3. **Audit and merge.** The [Code Audit Team](/workflow/code-audit-team/) reviews the pull request and GAIA fixes what it finds. Once the review passes, GAIA posts the `GAIA-Audit` check and asks whether to merge.

[Onboarding, as you build](/getting-started/onboarding/) walks through when each of these first steps in.

## Resuming work

When a session's context gets [heavy](/models-and-context/token-efficiency/#context-bands), GAIA saves your place and asks whether to continue or clear. If you choose to clear, GAIA prints a continuation prompt to paste after you `/clear`. You can also ask for one at any time. See [Resuming long work](/workflow/work-lifecycle/#resuming-long-work).

## Maintenance commands

<Aside type="note">
You rarely reach for these yourself, and you do not have to memorize them. Each one except `/gaia-forensics` surfaces on the [statusline](/workflow/statusline/#nudges) when it is due.
</Aside>

| When... | Reach for | Why |
| --- | --- | --- |
| Dependencies are stale or vulnerable | [`/update-deps`](/maintenance/update-deps/) | Resolves security advisories, then updates packages by group. |
| A new GAIA release is out | [`/update-gaia`](/maintenance/update-gaia/) | Merges the release into your project without overwriting your changes. |
| Memory or auto-loaded files have drifted | [`/gaia-cleanse`](/maintenance/cleanse/) | Finds instructions that repeat the wiki, contradict it, or are out of date. |
| The audit keeps flagging the same thing | [`/gaia-codify`](/maintenance/codify/) | Turns the recurring finding into a check, a skill, or a rule. |
| Accepted trade-offs have piled up | [`/gaia-residue`](/maintenance/residue/) | Goes through the known issues reviewers accepted at merge and dismisses, keeps, or turns each into a tech-debt issue. |
| The wiki has fallen behind the code | [`/gaia-wiki`](/maintenance/wiki/) | Updates the project wiki Claude reads from, merges overlapping pages, and fixes broken links and formatting. |
| The Claude integration feels off | [`/gaia-fitness`](/maintenance/fitness/) | Lints skills, rules, commands, agents, hooks, and settings, grades them, and heals your own files. |
| A GAIA command or hook misbehaved | [`/gaia-forensics`](/maintenance/forensics/) | Works out what went wrong and, if it is a bug, drafts a report ready to file. |
