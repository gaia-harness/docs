The `.notebook/` folder at the root of your main checkout is where GAIA keeps working material for SPECs, plans, and research. It is gitignored.

## An engineer's notebook

The notebook works like an engineer's paper notebook: you keep it at your own desk and write in it while the work is happening. It holds drafts, plans in progress, and notes on what you tried. It is not where the finished result lives.

The finished result is the code, the pull request, and the commit history. Before a plan's pull request is audited, Claude writes a short summary of what shipped and can promote it into the [project wiki](/maintenance/wiki/) on the same branch, so the lasting part travels with the code. After the merge, GAIA clears the notebook entry out.

Nothing in the notebook is committed, so drafts, dead ends, and research notes never show up in your history or a pull request's diff.

## What it holds

| Folder | Contents |
| --- | --- |
| `.notebook/specs/SPEC-NNN/` | A SPEC from [`/gaia-spec`](/workflow/spec/). Its plan sits inside it as `plan/` (a second plan is `plan-2/`). |
| `.notebook/plans/PLAN-NNN/` | A plan from [`/gaia-plan`](/workflow/plan/) that has no SPEC. |
| `.notebook/research/<date>-<topic>/` | Notes from research you ask Claude to do, with a small status file rewritten as it goes. |
| `.notebook/catalog.json` | GAIA's index of everything above. |

<Aside type="caution">
Do not delete or hand-edit `catalog.json`. It records where each SPEC draft stands and this machine's share of SPEC numbering, and no other copy exists. If it becomes unreadable, every GAIA command that writes to the notebook stops without changing anything. To recover, ask Claude:

```text
GAIA says .notebook/catalog.json is unreadable. Find out why and repair it without losing any SPEC drafts or numbering.
```
</Aside>

## How entries are cleared

GAIA clears out entries it no longer needs at the start of every `/gaia-spec` and `/gaia-plan`.

**SPECs and plans.** Once the pull request is ready to merge, Claude writes `SUMMARY.md` into the folder, describing what shipped. After the merge, the working files are removed and the summary kept. The summary is deleted 30 days later, but only once it is written and the work's cost is recorded in the [usage ledger](/models-and-context/cost/). A SPEC you abandon is deleted 30 days after you abandon it.

**Research.** Claude closes a research folder once its result lands somewhere tracked, such as code, a SPEC, or the wiki. Thirty days after it closed, and only when no open SPEC, plan, Claude memory file, issue, or pull request names it, `/gaia-spec` asks you to delete it, keep it, or snooze it for another 30 days. It asks only in an interactive session with the [GitHub CLI](https://cli.github.com/) (`gh`) signed in, since it checks GitHub for references. `/gaia-plan` only reports how many folders are ready.

To change the 30-day window, ask Claude, then restart Claude Code:

```text
Set GAIA_SPEC_RETENTION_DAYS to 60 in the env block of .claude/settings.local.json.
```

| Variable | Applies to | Default |
| --- | --- | --- |
| `GAIA_SPEC_RETENTION_DAYS` | SPEC and plan folders | 30 |
| `GAIA_RESEARCH_RETENTION_DAYS` | Research folders | 30 |

`.claude/settings.local.json` is your machine only, not committed.

## Why it stays on your machine

Your notebook is on your machine and your teammate's is on theirs. GAIA does not sync them.

- **It is working material, not the record.** Your team sees the work through the code, the pull request, and any wiki pages the summary was promoted into.
- **Its entries do not outlive the work.** A link to a deleted folder from a commit or pull request would break, so GAIA keeps those references out ([below](#notebook-references-stay-out-of-shared-history)).
- **Numbers do not travel.** Plan numbers come from your own catalog, so your `PLAN-003` and a teammate's are different plans. SPEC numbers are reserved by pushing a `spec/NNN` tag to your remote, so two people never get the same one. With no remote, or when the remote refuses the tag, numbering comes from your own catalog, and GAIA warns you. Either way, the SPEC stays in its author's notebook.

If something in your notebook should reach your team, put it somewhere tracked, such as the wiki or a rule in `.claude/rules/`.

## Notebook references stay out of shared history

A SPEC, UAT, or plan number (such as `SPEC-012`) or a path to a notebook entry means nothing to anyone else: it names a document on one machine, and only until it is cleared. GAIA catches these references where your team reads most, and Claude rewrites the text to describe the work instead:

| Where | What catches it |
| --- | --- |
| Commit messages | The `commit-msg` git hook |
| Lines a commit adds | The `pre-commit` git hook: prose files in full, code only in whole-line comments, skipping tests and fixtures |
| Pull request and issue titles and bodies | A Claude Code hook on `gh pr create`, `gh pr edit`, `gh issue create`, and `gh issue edit` |
| [Playwright](https://playwright.dev/) tests | A scan of `apps/web/.playwright/` while a plan runs |

Paths to a run folder under `.gaia/local/runs/` (GAIA's machine-local state) are caught too. Placeholders such as `SPEC-NNN` and plain issue numbers such as `#142` pass. If you commit by hand and hit one of these checks, reword the text or ask Claude to. See the [gate reference](/reference/gates/#machine-local-references).

## Worktrees share one notebook

Every [worktree](/workflow/work-lifecycle/#3-isolate) GAIA creates gets a `.notebook` link to the main checkout's folder, so a plan running in a worktree reads and writes the notebook you see, and removing the worktree removes nothing from it. This needs `.notebook` in the main checkout's `.gitignore`, where GAIA puts it.
