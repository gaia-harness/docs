`/gaia-plan` splits a feature into phases. Each phase delivers one behavior from start to finish. Its tasks can run at the same time, and the types and interfaces the tasks share (the contracts) are fixed up front so the pieces fit together. It writes a plan folder, not code, and gives you a prompt to paste into a fresh session, where an orchestrator (the session that runs the plan) builds it.

The plan folder is saved in the [Notebook](/workflow/notebook/).

## When to use it

Use `/gaia-plan` when the work spans several files or modules, or has parts that can be built at the same time, such as UI, services, and tests. For a one-line fix or a single-file edit, just ask Claude.

When the goal is not settled yet, run [`/gaia-spec`](/workflow/spec/) instead. It plans its SPEC in the same session. See [Spec, plan, or just do it](/workflow/work-lifecycle/#spec-plan-or-just-do-it).

## How to invoke

```
/gaia-plan a feature description in plain language
```

From a saved SPEC:

```
/gaia-plan SPEC-005
```

With no description, `/gaia-plan` asks for one.

### Auto mode

```
/gaia-plan auto a feature description
```

Auto mode is for runs nobody is watching. It removes two questions:

- **Planner model.** On a model other than Opus or Fable, the planner uses Opus without asking.
- **Plan audit.** Clear fixes are applied without asking. A finding with more than one reasonable fix is written to `## Audit notes` in the plan's `README.md`. Read it before you paste the kickoff prompt.

A description is required. A description whose first word is "auto" is read as auto mode, so reword it.

## What gets produced

| Plan | Folder |
|---|---|
| From a SPEC | `.notebook/specs/SPEC-NNN/plan/` (a second plan for the same SPEC is `plan-2/`) |
| With no SPEC | `.notebook/plans/PLAN-NNN/` |

Inside it:

| File | Purpose |
| --- | --- |
| `README.md` | The overview: phase order, the tasks in each phase and their models, the shared contracts, and the source SPEC. |
| `ORCHESTRATOR.md` | The orchestrator's step-by-step instructions: where the work runs, phases and quality gates, sub-agent prompts, the audit before merge, git steps, and when to stop. |
| `KICKOFF.md` | The prompt a fresh session reads to start. |
| `task-<name>.md` | One per task: contracts, files to change, acceptance criteria, dependencies. |
| `PROGRESS.md` | Written during execution: one entry per completed or halted phase. |

## The flow

1. **Before it starts.** GAIA clears out [notebook entries it no longer needs](/workflow/notebook/#how-entries-are-cleared), and Claude offers to pull when your GAIA version is behind the remote, or stops until you push your local `main` when it has unpushed commits. See [Out-of-date or unpushed main](/reference/gates/#out-of-date-or-unpushed-main).
2. **Find the SPEC**, if you named one. If none matches, it stops instead of planning without it.
3. **Pick the planner model.** On Opus or Fable the planner uses your model. Otherwise Claude asks: Opus (recommended), Fable, or your current model. The planner runs at your session's `/effort`, so a higher effort drafts a deeper plan.
4. **Plan.** A planner sub-agent writes the folder.
5. **Verify.** A script checks that every required file is there and every UAT in the SPEC is assigned to a task. For a SPEC's plan, it also sends back a phase with no UAT, unless the plan marks that phase as infrastructure (work with nothing a user can see) and says why.
6. **Plan audit.** Reviewers check the plan before anything is built from it. See [The plan audit](#the-plan-audit).
7. **Report.** A [cost line](/models-and-context/cost/#what-you-see), then the prompt:

   ```text
   Read /absolute/path/to/plan/KICKOFF.md and execute it.
   ```

   Type `/clear` and paste it.

## The plan audit

The [SPEC audit](/workflow/spec/#the-spec-audit) checks what to build, and the [Code Audit Team](/workflow/code-audit-team/) checks the finished code. The plan audit checks what neither sees: how the work is split, which tasks run side by side, and the contracts between them. A flaw caught here costs one edit to the plan, not a failed run.

It runs on any plan with tasks running side by side, several phases, or a shared contract. A simple plan (one or two tasks, one phase, nothing shared) skips it. If your session cannot start sub-agents, it is skipped with a note.

### The lenses

Each lens is a fresh sub-agent that reads the plan and your code for itself:

| Lens | What it checks |
| --- | --- |
| (DP) Decomposition and dependencies | Side-by-side tasks that share state, edit the same files, need each other's output, or run project-wide checks (lint, type checks, Playwright, a dev server) that would collide. A phase order that ignores a real dependency. A contract two tasks read differently. A phase marked as infrastructure that delivers something a user can see. |
| (CG) Contract grounding | Every file path, export, type, and signature a task names really exists in your code and installed packages. |
| (COV) SPEC coverage | For a SPEC's plan only: every UAT and success criterion is covered, no task contradicts the SPEC, and no task brings back work the SPEC ruled out. Each UAT's test starts from the state its Given describes, such as the same environment variable, seeded data, or server mode, never a different setup. |

These checks have a clear yes-or-no answer against your code, so there is no refutation pass.

### What you see

Critical and major findings are printed as one list headed **Plan audit**, each with its evidence and recommended fix, then one question: **Accept all as recommended** or **Revise**. Minor findings are applied without asking.

A finding about one spot, such as a wrong contract, is fixed in the plan's files. A finding that the task split itself is wrong sends the plan back to the planner, and the rewritten plan is verified again (step 5).

## Execution

The orchestrator runs in the fresh session:

- **Where it runs** follows your team's [isolation policy](/workflow/work-lifecycle/#3-isolate): a separate worktree by default. The branch is `<type>/spec-<nnn>-<slug>` for a SPEC's plan or `<type>/plan-<nnn>-<slug>` otherwise, where `<type>` is the change's Conventional Commits type. The pull request title's type must match.
- **Each phase** hands its tasks to sub-agents, Sonnet by default. Sub-agents only edit files. Each sub-agent typechecks its own work before it returns. A task that adds tests goes to two sub-agents in turn. The first writes only the tests and records each one [failing first](/workflow/tdd/#code-with-predictable-output-seen-failing-first). GAIA then checks that every new test has a recorded failure, and a reviewer checks that each test asserts what its task and SPEC call for, no more and no less, and that working code can pass it. A test that fails either check goes back to the first sub-agent once. A second miss stops the plan and names the test. Only then does the second sub-agent write the code, and it may not change those tests. The orchestrator commits each phase after the Quality Gate passes. See [Who does what](/workflow/work-lifecycle/#who-does-what).
- **A failed phase gate** gets one retry when each failing file belongs to one task and fails only on a typecheck or lint error, or is an acceptance test that does not itself make the call its checks read, such as a route test that leaves its loader or action call to a helper. Each of those tasks gets its errors in a fresh sub-agent, and the gate runs again. A browser or real-server test a task wrote itself, not from a UAT, goes to two fresh sub-agents at once when it fails as it runs. One may fix the test if it is wrong, never loosen a correct one, and the other may fix only the app code. A typecheck or lint error in that test goes to the test-writing sub-agent alone. A browser or real-server test from outside the phase that passed before and now fails goes to the sub-agents whose app code the phase changed, and they never edit the test. One retry covers every failure in the gate. Any other failure (any other test or UAT failure, an outside test with no earlier pass or that fails because of the test environment, a typecheck or lint error in any other test a task wrote, an error no single task owns, a new test the [seen-failing-first check](/reference/gates/#test-seen-failing-first-red-gate) refuses because its code already exists, or a second failure in the same phase) stops the plan. A stop asks you one question, with **Stay halted** recommended, or **Discuss this** to talk it through.
- **A task that runs out of context** hands off to a fresh sub-agent. A task that would need a third handoff stops the plan and tells you.
- **The pull request** opens as a draft. The orchestrator runs the [worthiness step](/workflow/tdd/#the-worthiness-step), the [overlap pass](/workflow/tdd/#the-overlap-pass), and the wiki update before the [Code Audit Team](/workflow/code-audit-team/) reviews it. Once the team clears it, the orchestrator shows a summary and the cost of the implementation, then asks you before it merges, with holding the merge as the recommended answer.

### Resuming a plan

Running the kickoff again on a plan with completed phases shows each one with its commit and asks:

- **Resume** at the first incomplete phase
- **Restart from Phase 1**
- **Abandon**: stop without running, committing, merging, or deleting anything

If the working tree has uncommitted changes, the plan does not resume. It asks the same **Stay halted** or **Discuss this** question and never offers to stash, discard, or commit your changes.

A plan keeps the steps it was generated with, even after a GAIA update, until you regenerate it.

### UAT specs

[`/gaia-spec`](/workflow/spec/#uats) writes the UATs. The planner routes each one to the lowest layer that can show its outcome, because a browser is the slowest and most expensive way to check anything:

| Route | When | How it is tested |
| --- | --- | --- |
| Story | One component, given its props, shows the outcome | An acceptance criterion in the owning task, tested on a [Storybook](https://storybook.js.org/) story |
| Route | A request to a route shows it: a status, a redirect, returned data, a validation error, an authorization outcome, or a side effect. This holds even when the SPEC words it as page text, such as a heading that shows data the loader returns, or names the page or error page that shows a refusal or error | A [Vitest](https://vitest.dev/) test that calls the route's loader or action |
| Real server | It needs the live server but not a browser, such as middleware, the HTTP status a guarded route serves for a refusal, cookies and the session, a forged request whose guard a direct loader or action call skips, the form the server serves, a flow through several plain HTML forms, or server-rendered HTML that is itself the SPEC's requirement. When a UAT's guard and its served HTML are separate requirements, the UAT gets a route test and its phase adds a real-server check. The plan names, for each one, what a route test cannot show, and GAIA's plan check refuses a real-server test with no reason given | A [Playwright](https://playwright.dev/) test that sends requests to the dev server and opens no page |
| Browser | It needs client JavaScript (an update without a reload), layout or position on screen, focus or the keyboard, an accessibility scan of the rendered page, or browser navigation such as the back button. Nothing else needs a browser. JavaScript turned off, or a plain HTML form, only rules out the browser, and the UAT routes by the rows above. The plan names which one each browser test needs, and GAIA's plan check holds Claude to it | A Playwright test that walks one user flow in a real page |
| Non-UI | Harness, script, or documentation behavior | Assigned to the phase that owns it |

Before Phase 1, each route, real-server, and browser UAT becomes a test that is expected to fail, under `apps/web/app/route-tests/<feature>/tests/` or `apps/web/.playwright/e2e/`, committed on its own. The cases the SPEC lists for a UAT are rows of that one test, never a second test file. The phase that owns a test cannot commit until it passes, and sub-agents may not change its assertions to make it pass. A plan with an authorization UAT also gets one live-server check per guarded route.

Before the audit, the [`uat-fidelity-judge`](/reference/agents/#uat-fidelity-judge) agent checks that each test still tests what the SPEC says. When the code and a UAT no longer agree, the plan stops so you can [reopen the SPEC](/workflow/spec/#reopening-a-saved-spec).
