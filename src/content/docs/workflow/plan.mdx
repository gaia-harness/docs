title: /gaia-plan
description: Split a feature into phases of tasks that sub-agents build. Produces a plan folder and a kickoff prompt you paste into a fresh session.
---

`/gaia-plan` splits a feature into phases. Each phase delivers one behavior from start to finish. Its tasks can run at the same time, and the types and interfaces the tasks share (the contracts) are fixed up front so the pieces fit together. It writes a plan folder, not code, and gives you a prompt to paste into a fresh session, where an orchestrator (the session that runs the plan) builds it.

The plan folder is saved in the [Notebook](/workflow/notebook/).

## When to use it

Use `/gaia-plan` when the work spans several files or modules, or has parts that can be built at the same time, such as UI, services, and tests. For a one-line fix or a single-file edit, just ask Claude.

When the goal is not settled yet, run [`/gaia-spec`](/workflow/spec/) instead. It plans its SPEC in the same session. See [Spec, plan, or just do it](/workflow/work-lifecycle/#spec-plan-or-just-do-it).

## How to invoke

```
/gaia-plan a feature description in plain language
```

From a saved SPEC:

```
/gaia-plan SPEC-005
```

With no description, `/gaia-plan` asks for one.

### Auto mode

```
/gaia-plan auto a feature description
```

Auto mode is for runs nobody is watching. It removes two questions:

- **Planner model.** On a model other than Opus or Fable, the planner uses Opus without asking.
- **Plan audit.** Clear fixes are applied without asking. A finding with more than one reasonable fix is written to `## Audit notes` in the plan's `README.md`. A plan that retires a security test, even the test of code the plan deletes, or a fix that would remove a security row or clear its flag, is also listed there, held for you to decide before merge. The security row stays until you rule on it, unless it is a newly planned row whose every case another security row of the same kind already checks; that one is removed and noted there. When the planner rewrites the plan and loses a security row, GAIA restores it and notes it there (it only notes a row for code the plan deletes, one it cannot pick out for sure, or one whose case was only reworded), and stops the run, naming the row, if the restored plan no longer verifies. Read it before you paste the kickoff prompt.

A headless run has nobody to answer questions, so with or without `auto` the planner uses Opus and every security test retire is held for you before merge.

A description is required. A description whose first word is "auto" is read as auto mode, so reword it.

## What gets produced

| Plan | Folder |
|---|---|
| From a SPEC | `.notebook/specs/SPEC-NNN/plan/` (a second plan for the same SPEC is `plan-2/`) |
| With no SPEC | `.notebook/plans/PLAN-NNN/` |

Inside it:

| File | Purpose |
| --- | --- |
| `README.md` | The overview: phase order, the tasks in each phase and their models, the shared contracts, and the source SPEC. |
| `ORCHESTRATOR.md` | The orchestrator's step-by-step instructions: where the work runs, phases and quality gates, sub-agent prompts, the audit before merge, git steps, and when to stop. |
| `KICKOFF.md` | The prompt a fresh session reads to start. |
| `task-<name>.md` | One per task: contracts, files to change, acceptance criteria, the tests it writes, dependencies. |
| `tests.json` | Holds the [test-design table](/workflow/testing/#the-test-design-table), which lists every planned test, its layer, and what to do with it. `README.md` shows it as a table, and a frozen copy is kept once the plan is approved. |
| `PROGRESS.md` | Written during execution: one entry per completed or halted phase. |

## The flow

1. **Before it starts.** GAIA clears out [notebook entries it no longer needs](/workflow/notebook/#how-entries-are-cleared), and Claude offers to pull when your GAIA version is behind the remote, or stops until you push your local `main` when it has unpushed commits. See [Out-of-date or unpushed main](/reference/gates/#out-of-date-or-unpushed-main).
2. **Find the SPEC**, if you named one. If none matches, it stops instead of planning without it.
3. **Pick the planner model.** On Opus or Fable the planner uses your model. Otherwise Claude asks: Opus (recommended), Fable, or your current model. The planner runs at your session's `/effort`, so a higher effort drafts a deeper plan.
4. **Plan.** A planner sub-agent writes the folder.
5. **Verify.** A script checks that every required file is there. For a SPEC's plan, it also checks that each [critical flow](/workflow/spec/#critical-flows) belongs to exactly one task in the [closing flow-test phase](#flow-tests), or is one the plan records as [covered by build tests](#flow-tests), that the task names the flow's test file at its expected path, and that the phase runs every flow test before it commits. For every plan, it checks that each requirement has a row in the test-design table, or, for a scope boundary or SPEC audit instruction that only steers the build, a record of what it directs, and that each task names exactly the tests its rows give it. For a rule stated as which roles may take each action, or which statuses each action starts from, it checks that some row tests every action with every role, and every action with every status, and that each role that may take an action is tested at every status. It also checks that no [security row](/workflow/testing/#security-tests) holds cases of two kinds.
6. **Plan audit.** Reviewers check the plan before anything is built from it. See [The plan audit](#the-plan-audit). The test-design table is then approved and frozen.
7. **Report.** A [cost line](/models-and-context/cost/#what-you-see), then the prompt:

   ```text
   Read /absolute/path/to/plan/KICKOFF.md and execute it.
   ```

   Type `/clear` and paste it.

## The plan audit

The [SPEC audit](/workflow/spec/#the-spec-audit) checks what to build, and the [Code Audit Team](/workflow/code-audit-team/) checks the finished code. The plan audit checks what neither sees: how the work is split, which tasks run side by side, and the contracts between them. A flaw caught here costs one edit to the plan, not a failed run.

The test-design lens runs on every plan. The other lenses run on any plan with tasks running side by side, several phases, or a shared contract, and a simple plan (one or two tasks, one phase, nothing shared) skips them. If your session cannot start sub-agents, the other lenses are skipped with a note and the test-design review runs in your session.

### The lenses

Each lens is a fresh sub-agent that reads the plan and your code for itself:

| Lens | What it checks |
| --- | --- |
| (DP) Decomposition and dependencies | Side-by-side tasks that share state, edit the same files, need each other's output, or run project-wide checks (lint, type checks, Playwright, a dev server) that would collide. A phase order that ignores a real dependency. A contract two tasks read differently. Acceptance criteria that cannot be checked on their own. Missing or miswired test setup, such as a mock handler or seed data, that another test would catch is fixed in the task that owns the setup, never with a new test. |
| (CG) Contract grounding | Every file path, export, type, and signature a task names really exists in your code and installed packages. |
| (COV) SPEC coverage | For a SPEC's plan only. Every flow, success criterion, scope rule, and question the SPEC answered is covered by a task. Each flow has one task in the closing phase that names its test file, or is recorded as covered by build tests, and that record is flagged when the flow has a step a flow test would keep or a step none of those tests checks. No build phase writes a flow test, no task contradicts the SPEC, and no task brings back work the SPEC ruled out. |
| (TD) Test design | Checks the [test-design table](/workflow/testing/#the-test-design-table) against GAIA's testing rules, the requirements, and your existing tests. Every requirement and case has a row. A scope boundary or SPEC audit instruction recorded as only steering the build is flagged as a missing test when it does state app behavior, and the rows written for one that only steers the build are removed and it is recorded instead. A condition with several parts needs a row for each part, and a rule about the order of checks needs one for each pair of neighboring checks. Every guard has a test of its own, not only the flow test, and every signed or encrypted value has a test that sends a forged or edited one. Every redirect target or callback URL the server uses has a test that sends one outside the allowed destinations. Every role, accessible name, exact wording, or attribute, such as a field's `name`, that the SPEC or a document it says to read first states has a test that checks it. Naming one in a task for its builder does not count until a test checks it. A case of a status, transition, or role rule that is tested only through a page or route test moves into the rule's one table of cases, and the rule's function takes every input a case varies. A rule stated as which roles may take each action, or which statuses each action starts from, gets a case for each action with each role, allowed or not, and for each action with each status, allowed or not. A role case uses a status the action allows, and a status case a role it allows, so each case tests one thing. Every role that may take an action has at least one case at each status. A final status is a case for every action. One example per requirement is not enough, and a row names each case by its values, never as "every role" or one sample. The table lists such a rule's actions, roles, and statuses, every one the requirements name, allowed or not, so the verify step (step 5) can check each pairing has a row. A rule left out of that list, or a list missing one the requirements name, is fixed here. A stated mapping from a value the app reads to what it shows, such as a stored `2` shown as `Shipped`, has a case for each value, tested where the mapping runs: a route test, a helper's unit test, or a story given the raw value, never a story given the already mapped text. It also trims a flow test row to the steps only the flow layer shows (its happy-path journey, the happy path's effects that take several requests or sessions, and its no-JavaScript happy-path posts), and drops a row left empty. A flow left with no row is recorded as covered by build tests. It also flags a row on the wrong layer, such as a unit test of a request outcome or a middleware guard's refusal, or a security row on a story with no route or real-server test beside it, two rows checking one behavior (the row on the layer GAIA's testing rules pick stays, and stated wording stays on its story or route test, with a real-server row checking the same thing cut back to the element being in the served HTML when that HTML is itself required, or dropped; a page title or meta description stays on its real-server row, a real-server check of a served error page, such as a 404, is cut back to the status, and the served-status check a guarded route needs is never a duplicate), a test nothing asked for, a route test for a success path the closing [flow test](#flow-tests) already walks and checks, unless the route test checks something the flow cannot see (the flow sees an effect when a later step checks its result, such as an item gone from a list it reads again), a test whose only catch beyond another app test of the same path is the app disagreeing with a mock, fixture, or seed data, a new test that should reuse or replace an existing one, and a row marked or not marked as a [security row](/workflow/testing/#security-tests) by mistake, such as a sign-in refusal left unmarked, judged case by case so a refusal that shares a test with an allowed case gets its own marked row. Any test row a fix adds, changes, or trims, from any lens including this one, any row another finding is folded into, and any row a rewrite by the planner adds or changes, gets the same checks in its new form before it is applied. It is reshaped when one change passes them all, otherwise dropped, and listed for you either way. A drop that leaves a requirement with no test is listed as an uncovered requirement, with a test that passes every check recommended. |

The DP, CG, and COV checks have a clear yes-or-no answer against your code, so they get no refutation pass. A test-design finding is a judgment call, such as which layer a test belongs on, so a separate sub-agent tries to disprove each critical or major one before it counts.

### What you see

Critical and major findings are printed as one list headed **Plan audit**, each with its evidence and recommended fix, then one question: **Accept all as recommended** or **Revise**. Each planned retire of a security test whose code the plan keeps is listed too, counting retires any fix adds, minor ones included, recommended to hold for you to decide before merge. Revising one can only drop the retire, so the test stays. Retiring the security test of code the plan deletes is not listed, since approving the plan approves it. Minor findings are applied without asking, with one exception: no fix removes a security row or clears its flag on its own. That row stays and is listed as its own item, recommended to keep, and only your ruling removes it. A newly planned security row whose every case another security row of the same kind already checks is listed too, recommended to remove. Once the fixes apply, GAIA checks each unmarked row that retires or changes a test in the same file, for the same requirement, as a security row. Any it marks as a security row is shown on a follow-up list, recommended to keep the mark, and the plan waits for your answer.

A finding about one spot, such as a wrong contract, is fixed in the plan's files. A finding that the task split itself is wrong sends the plan back to the planner, and the rewritten plan is verified again (step 5). GAIA then compares the old and new test-design tables. Each security row the rewrite dropped, unmarked, or gave another kind is shown on a second list, recommended to restore, before the plan is approved. A dropped row for the security test of code the rewritten plan deletes is recommended to drop instead. A security test the rewrite kept in the same file and title but with a reworded case is listed with the old and new case, recommended to keep. Revising it restores the old case.

## Execution

The orchestrator runs in the fresh session:

- **Where it runs** follows your team's [isolation policy](/workflow/work-lifecycle/#3-isolate): a separate worktree by default. The branch is `<type>/spec-<nnn>-<slug>` for a SPEC's plan or `<type>/plan-<nnn>-<slug>` otherwise, where `<type>` is the change's Conventional Commits type. The pull request title's type must match.
- **Each phase** hands its tasks to sub-agents, Sonnet by default. Sub-agents only edit files. Each one builds its task, writes the tests the [test-design table](/workflow/testing/#the-test-design-table) gives it, under their planned titles, and typechecks and lints its own files before it returns, so the phase gate's automatic lint fixes do not undo its work. Every refusal, guard, or validation a task builds gets a test named in that task that makes it refuse, at the lowest layer that shows it (usually a route test), never left to a [flow test](#flow-tests). A value that must never appear somewhere, such as a token kept out of the page or a cookie, counts as a guard too. Its test runs while the value is present, such as a session that holds the token, and checks that it stays out of that place, at the lowest layer that shows it. A signed or encrypted value, such as a session cookie or a token, counts as a guard as well. Its test sends a forged or edited value and checks that the app refuses it. So does a redirect target or callback URL the server uses. Its test sends one outside the allowed destinations and checks that the app refuses it or swaps in an allowed one. When a SPEC requirement lists several cases, a test named in the task checks every case, except a case that is not a guard and that the flow test checks. A condition with several parts, such as an open, unlocked account, is one case per part. A rule about the order of checks is one case per pair of neighboring checks. Its test passes every check before the pair, fails both checks in the pair, and checks that the earlier one refused. A rule about statuses, roles, or moves between states keeps all its cases in one table. A role, accessible name, or exact wording that the SPEC or a document the SPEC says to read first states also gets a test, usually the page's story, that checks the stated text itself rather than the app's own copy of it, so a later fix cannot change it unnoticed. A test that already checks it counts. Where the SPEC and that document disagree, the SPEC's wording is the one tested. The phase gate runs typecheck, lint, and the existing tests, and the orchestrator commits each phase once it passes. See [Who does what](/workflow/work-lifecycle/#who-does-what).
- **Security tests** for a phase are written by a separate sub-agent once its tasks return and before its gate. See [Security tests](/workflow/testing/#security-tests).
- **A failed phase gate** can be retried in these four cases. Each phase gets two retries: one for a gate that failed only on typecheck or lint, and one for a gate with a failing test. So a lint fix never uses up the retry a later test failure needs. Each retry covers every failure in the gate.
  - A typecheck or lint error in files that each belong to one task, or in a test file several tasks of the phase share. Each of those tasks gets its errors in a fresh sub-agent. Errors in a shared test file go to the same single sub-agent that fixes that file's failing tests (below). It fixes an error whose cause is in that test file, edits nothing else, and passes a cause it finds in another task's file on to that task.
  - A [flow test](#flow-tests) that fails in the closing phase. It goes to a fresh sub-agent for the task that owns it, which may fix the code or the test, whichever is wrong.
  - A test of any kind that fails in a file one of the phase's tasks owns, when the test environment is not the cause. It goes to a fresh sub-agent for that task, which fixes the code, or updates the test when the phase changed that behavior on purpose. When several tasks of the phase share the test file, one fresh sub-agent fixes that file's failing tests and their shared setup, and edits nothing else. When the cause is in another file that one task of the phase owns, the same retry goes on to that task.
  - A Playwright test from outside the phase that passed before and now fails, when the test environment is not the cause. It goes to the sub-agents whose app code the phase changed. They fix the code, or update the test when the phase changed that behavior on purpose.

  No retry changes a label, role, message, or URL that the SPEC states just to match the code. The gate then runs again. Any other failure, or a second failure of the same kind in the same phase, stops the plan. A stop asks you one question, with **Stay halted** recommended, or **Discuss this** to talk it through. When the fix is a step only you can take, such as adding a variable to `apps/web/.env`, it recommends **I did it** instead, with **Stay halted** second. GAIA then runs the phase gate again and continues only if it passes. If it fails again, the run ends without another question.
- **A task that runs out of context** hands off to a fresh sub-agent. A task that would need a third handoff stops the plan and tells you.
- **The simplify pass** runs once, after the last phase commits. A sub-agent runs the `simplify` skill over the whole branch, and the orchestrator commits its edits through the [Quality Gate](/workflow/code-audit-team/#what-it-checks). If the gate fails or the pass stops partway, the edits are discarded and saved as a patch. Only a refused push or a failed discard stops the plan. The final summary says whether the pass applied, changed nothing, did not run, or was discarded, and where any patch is.
- **The pull request** opens as a draft after the first phase commits. After the simplify pass, the orchestrator runs the [checks on each flow test](#flow-tests) for a SPEC's plan, then the [drift check](/workflow/testing/#the-drift-check) and the wiki update, all before the [Code Audit Team](/workflow/code-audit-team/) reviews it. Once the team clears it, the orchestrator shows a summary and the cost of the implementation, then waits for the required checks and asks you before it merges. It recommends **Merge it** when the merge is ready, and **Hold the merge** only for a reason it names, such as a failed required check, a residual you have not answered, or a way the built app differs from the SPEC that you have not decided on.

### Resuming a plan

Running the kickoff again on a plan with completed phases shows each one with its commit and asks:

- **Resume** at the first incomplete phase
- **Restart from Phase 1**
- **Abandon**: stop without running, committing, merging, or deleting anything

When every phase is already complete, the run picks up at the simplify pass and skips any step that already finished.

If the working tree has uncommitted changes, the plan does not resume. It asks the same **Stay halted** or **Discuss this** question and never offers to stash, discard, or commit your changes.

A plan keeps the steps it was generated with, even after a GAIA update, until you regenerate it. Its test-design table is still checked by the updated GAIA, so when an update tightens that check, [the update's summary](/maintenance/update-gaia/) says what an older plan's table needs. Ask Claude to add it, or regenerate the plan.

### Flow tests

A plan built from a SPEC ends with one closing phase after the build. It has one task per [critical flow](/workflow/spec/#critical-flows), each writing that flow's test, and no earlier phase writes one.

A flow left with nothing a flow test keeps (see below) gets no flow test. That happens when every step is a refusal a build task's test already checks, such as a signed-out visitor sent to sign-in, or when its steps only open a page to see wording or state that a lower-layer test already checks. The plan records the build tests that cover its steps instead.

- **A web flow** gets one [Playwright](https://playwright.dev/) test at `apps/web/.playwright/flows/<name>.spec.ts`, where `<name>` is the flow's short name. A comment at its top, the `@covers` line, names the app folders the flow runs through.
- **A command-line flow** gets the test file the SPEC names.

Each flow test is one file. It walks the flow's journey through its happy path, plus only the happy path's effects that take several requests or sessions to set up, such as signing out ending the session, so the protected page then sends the user to sign-in. Where the SPEC requires the flow to work without JavaScript, it also posts the happy path's forms to the server the way a browser without JavaScript would, in the same file and without opening a page, building each body from the form the server returns. A separate real-server test file for those posts is also accepted. An error path the SPEC says must work without JavaScript gets no such post, since the action's route test and the page's story cover it. The flow test checks no page markup or ARIA attributes beyond a role or accessible name the SPEC or a document it says to read first states, repeats no refusal that a build task's test or another flow test already checks, however many requests or sessions it takes to set up, and checks no stated wording or state that a lower-layer test owns. The closing phase's gate runs every flow test before it commits.

After the last phase, GAIA checks each flow. A flow covered by build tests must still match its record. Any other flow's test file must exist and have changed on the branch, and a SPEC or flow id such as `FLOW-001` must not appear in it. A web flow's test must also be one Playwright runs, with an `@covers` line that names every folder the SPEC lists for the flow and the branch changed. A failed check goes to the sub-agent for the task that owns that flow, for one round of fixes, and then the checks run again. A second failure, a failure no task owns, or a check that cannot run stops the plan with the same **Stay halted** or **Discuss this** question.

The [drift check](/workflow/testing/#the-drift-check) then judges each flow test.
