description: Split a feature into phases of tasks that sub-agents build. Produces a plan folder and a kickoff prompt you paste into a fresh session.
---

`/gaia-plan` splits a feature into phases. Each phase delivers one behavior from start to finish. Its tasks can run at the same time, and the types and interfaces the tasks share (the contracts) are fixed up front so the pieces fit together. It writes a plan folder, not code, and gives you a prompt to paste into a fresh session, where an orchestrator (the session that runs the plan) builds it.

The plan folder is saved in the [Notebook](/workflow/notebook/).

## When to use it

Use `/gaia-plan` when the work spans several files or modules, or has parts that can be built at the same time, such as UI, services, and tests. For a one-line fix or a single-file edit, just ask Claude.

When the goal is not settled yet, run [`/gaia-spec`](/workflow/spec/) instead. It plans its SPEC in the same session. See [Spec, plan, or just do it](/workflow/work-lifecycle/#spec-plan-or-just-do-it).

## How to invoke

```
/gaia-plan a feature description in plain language
```

From a saved SPEC:

```
/gaia-plan SPEC-005
```

With no description, `/gaia-plan` asks for one.

### Auto mode

```
/gaia-plan auto a feature description
```

Auto mode is for runs nobody is watching. It removes three questions:

- **Planner model.** On a model other than Opus or Fable, the planner uses Opus without asking.
- **Plan review.** Clear fixes are applied without asking. A finding with more than one reasonable fix leaves the plan unchanged and is written to `## Audit notes` in the plan's `README.md`. Read it before you paste the kickoff prompt.
- **Test stage.** The [test stage](/workflow/test-stage/) runs without asking.

A headless run has nobody to answer questions, so with or without `auto` the planner uses Opus and the test stage runs.

A description is required. A description whose first word is "auto" is read as auto mode, so reword it.

## What gets produced

| Plan | Folder |
|---|---|
| From a SPEC | `.notebook/specs/SPEC-NNN/plan/` (a second plan for the same SPEC is `plan-2/`) |
| With no SPEC | `.notebook/plans/PLAN-NNN/` |

Inside it:

| File | Purpose |
| --- | --- |
| `README.md` | The overview: phase order, the tasks in each phase and their models, the shared contracts, and the source SPEC. |
| `ORCHESTRATOR.md` | The orchestrator's step-by-step instructions: where the work runs, phases and quality gates, sub-agent prompts, the audit before merge, git steps, and when to stop. |
| `KICKOFF.md` | The prompt a fresh session reads to start. |
| `task-<name>.md` | One per task: the files to read first, contracts, files to change, acceptance criteria, dependencies, and the tests the [test stage](/workflow/test-stage/) lists for it. |
| `TEST-STAGE` | Whether the test stage ran or was skipped. |
| `PROGRESS.md` | Written during execution: one entry per completed or halted phase. |

## The flow

1. **Before it starts.** GAIA clears out [notebook entries it no longer needs](/workflow/notebook/#how-entries-are-cleared), and Claude offers to pull when your GAIA version is behind the remote, or stops until you push your local `main` when it has unpushed commits. See [Out-of-date or unpushed main](/reference/gates/#out-of-date-or-unpushed-main).
2. **Find the SPEC**, if you named one. If none matches, it stops instead of planning without it.
3. **Pick the planner model.** On Opus or Fable the planner uses your model. Otherwise Claude asks: Opus (recommended), Fable, or your current model. The planner runs at your session's `/effort`, so a higher effort drafts a deeper plan.
4. **Plan.** A planner sub-agent writes the folder.
5. **Verify.** A script checks that every required file is there and that the orchestrator's instructions carry every step they need, word for word. For a SPEC's plan, it also checks that each task belongs to exactly one phase.
6. **Plan review.** Reviewers check the plan before anything is built from it. See [The plan review](#the-plan-review).
7. **Test stage.** Claude asks whether to run the [test stage](/workflow/test-stage/), which decides each task's tests, with **Run the test stage** recommended, or **Skip**.
8. **Report.** A [cost line](/models-and-context/cost/#what-you-see), a note when you skipped the test stage, then the prompt:

   ```text
   Read /absolute/path/to/plan/KICKOFF.md and execute it.
   ```

   Type `/clear` and paste it.

## The plan review

The [SPEC review](/workflow/spec/#the-spec-review) checks what to build, and the [Code Audit Team](/workflow/code-audit-team/) checks the finished code. The plan review checks what neither sees: how the work is split, which tasks run side by side, the contracts between them, and whether every part of the SPEC has a task. A flaw caught here costs one edit to the plan, not a failed run.

It runs on any plan with tasks running side by side, several phases, or a shared contract. A simple plan (one or two tasks, one phase, nothing shared) skips it. If your session cannot start sub-agents, it is skipped with a note, and each phase's checks and the Code Audit Team still run.

### The lenses

Each lens is a fresh sub-agent that reads the plan and your code for itself:

| Lens | What it checks |
| --- | --- |
| (DP) Decomposition and dependencies | Side-by-side tasks that share state, edit the same files, need each other's output, or run project-wide checks (lint, type checks, Playwright, a dev server) that would collide. A phase order that ignores a real dependency. A contract two tasks read differently. Acceptance criteria that cannot be checked on their own. A way every task passes its checks yet the app crashes when it really starts, such as a setting the production start never sets. |
| (CG) Contract grounding | Every file path, export, type, signature, and setting a task names really exists in your code and installed packages. |
| (COV) SPEC coverage | For a SPEC's plan only. Every flow, success criterion, scope rule, and question the SPEC answered is covered by a task, including values the SPEC points to in `REQUIREMENTS.md`. No task contradicts the SPEC, and no task brings back work the SPEC ruled out. |

Each of these lenses' findings has a clear yes-or-no answer against your code, so no reviewer tries to disprove them.

### What you see

Critical and major findings are printed as one list headed **Plan review**, each with its evidence and recommended fix, then one question: **Accept all as recommended** or **Revise**. Minor findings are applied without asking.

A finding about one spot, such as a wrong contract, is fixed in the plan's files and noted under `## Audit notes` in `README.md`. A fix that removes or rewrites an acceptance criterion must say where each case it removed now lives, and a script checks it, as in the [SPEC review](/workflow/spec/#the-fixer). A finding that the task split itself is wrong sends the plan back to the planner, and the rewritten plan is verified again (step 5).

## Execution

The orchestrator runs in the fresh session:

- **Where it runs** follows your team's [isolation policy](/workflow/work-lifecycle/#3-isolate): a separate worktree by default. The branch is `<type>/spec-<nnn>-<slug>` for a SPEC's plan or `<type>/plan-<nnn>-<slug>` otherwise, where `<type>` is the change's Conventional Commits type. The pull request title's type must match.
- **Each phase** hands its tasks to sub-agents, Sonnet by default. Sub-agents only edit files. Each one builds its task, writes the tests the [test stage](/workflow/test-stage/) listed for it, under their listed titles and no others, and typechecks and lints its own files before it returns, so the phase gate's automatic lint fixes do not undo its work. A test it thinks is worth adding beyond its list is reported, not written. The phase gate runs typecheck, lint, and the existing tests, and the orchestrator commits each phase once it passes. See [Who does what](/workflow/work-lifecycle/#who-does-what).
- **Security tests** for a phase are written by a separate sub-agent once its tasks return and before its gate. See [Security tests](/workflow/testing/#security-tests).
- **A failed phase gate** can be retried in these four cases. Each phase gets two retries: one for a gate that failed only on typecheck, lint, or a file's length limit, and one for a gate with a failing test. So a lint fix never uses up the retry a later test failure needs. Each retry covers every failure in the gate.
  - A typecheck or lint error, or a file over its length limit, in files that each belong to one task, or in a test file several tasks of the phase share. Each of those tasks gets its errors in a fresh sub-agent. A file over its length limit is split, with whole functions or sections moved into a new or existing helper file beside it, never by trimming wording or raising the limit. Errors in a shared test file go to the same single sub-agent that fixes that file's failing tests (below). It fixes an error whose cause is in that test file, edits nothing else, and passes a cause it finds in another task's file on to that task.
  - A [flow test](#flow-tests) that fails in the closing phase. It goes to a fresh sub-agent for the task that owns it, which may fix the code or the test, whichever is wrong.
  - A test of any kind that fails in a file one of the phase's tasks owns, when the test environment is not the cause. It goes to a fresh sub-agent for that task, which fixes the code, or updates the test when the phase changed that behavior on purpose. When several tasks of the phase share the test file, one fresh sub-agent fixes that file's failing tests and their shared setup, and edits nothing else. When the cause is in another file that one task of the phase owns, the same retry goes on to that task.
  - A Playwright test from outside the phase that passed before and now fails, when the test environment is not the cause. It goes to the sub-agents whose app code the phase changed. They fix the code, or update the test when the phase changed that behavior on purpose.

  No retry changes a label, role, message, or URL that the SPEC states just to match the code. The gate then runs again. Any other failure, or a second failure of the same kind in the same phase, stops the plan. A stop asks you one question, with **Stay halted** recommended, or **Discuss this** to talk it through. When the fix is a step only you can take, such as adding a variable to `apps/web/.env`, it recommends **I did it** instead, with **Stay halted** second. GAIA then runs the phase gate again and continues only if it passes. If it fails again, the run ends without another question.
- **A task that runs out of context** hands off to a fresh sub-agent. A task that would need a third handoff stops the plan and tells you.
- **The simplify pass** runs once, after the last phase commits. A sub-agent runs the `simplify` skill over the whole branch, and the orchestrator commits its edits through the [Quality Gate](/workflow/code-audit-team/#what-it-checks). If the gate fails or the pass stops partway, the edits are discarded and saved as a patch. Only a refused push or a failed discard stops the plan. The final summary says whether the pass applied, changed nothing, did not run, or was discarded, and where any patch is.
- **The pull request** opens as a draft after the first phase commits. After the simplify pass, the orchestrator runs the [checks on each flow test](#flow-tests) for a SPEC's plan, then the wiki update, then the [worthiness step](/workflow/testing/#the-worthiness-step), all before the [Code Audit Team](/workflow/code-audit-team/) reviews it. Once the team clears it, the orchestrator shows a summary and the cost of the implementation, then waits for the required checks and asks you before it merges. It recommends **Merge it** when the merge is ready, and **Hold the merge** only for a reason it names, such as a failed required check, a residual you have not answered, or a way the built app differs from the SPEC that you have not decided on.

### Resuming a plan

Running the kickoff again on a plan with completed phases shows each one with its commit and asks:

- **Resume** at the first incomplete phase
- **Restart from Phase 1**
- **Abandon**: stop without running, committing, merging, or deleting anything

When every phase is already complete, the run picks up at the simplify pass and skips any step that already finished.

If the working tree has uncommitted changes, the plan does not resume. It asks the same **Stay halted** or **Discuss this** question and never offers to stash, discard, or commit your changes.

A plan keeps the steps it was generated with, even after a GAIA update, until you regenerate it.

### Flow tests

A plan built from a SPEC ends with one closing phase after the build, which the [test stage](/workflow/test-stage/) adds. It has one task per [critical flow](/workflow/spec/#critical-flows), each writing that flow's test, and no earlier phase writes one.

- **A web flow** gets one [Playwright](https://playwright.dev/) test at `apps/web/.playwright/flows/<name>.spec.ts`, where `<name>` is the flow's short name. A comment at its top, the `@covers` line, names the app folders the flow runs through.
- **A command-line flow** gets the test file the SPEC names.

Each flow test is one file. It walks the flow's journey through its happy path, plus only the happy path's effects that take several requests or sessions to set up, such as signing out ending the session, so the protected page then sends the user to sign-in. Where the SPEC requires the flow to work without JavaScript, it also posts the happy path's forms to the server the way a browser without JavaScript would, in the same file and without opening a page, building each body from the form the server returns. A separate real-server test file for those posts is also accepted. An error path the SPEC says must work without JavaScript gets no such post, since the action's route test and the page's story cover it. The flow test checks no page markup or ARIA attributes beyond a role or accessible name the SPEC or a document it says to read first states, repeats no refusal that a build task's test or another flow test already checks, however many requests or sessions it takes to set up, and checks no stated wording or state that a lower-layer test owns. The closing phase's gate runs every flow test before it commits.

After the last phase, GAIA checks each flow. Its test file must exist and have changed on the branch, and a SPEC or flow id such as `FLOW-001` must not appear in it. A web flow's test must also be one Playwright runs, with an `@covers` line that names every folder the SPEC lists for the flow and the branch changed. A failed check goes to the sub-agent for the task that owns that flow, for one round of fixes, and then the checks run again. A second failure, a failure no task owns, or a check that cannot run stops the plan with the same **Stay halted** or **Discuss this** question. When the test stage was skipped, a flow with no test is reported as a gap instead, not a failure.

The [worthiness review](/workflow/testing/#the-worthiness-review) then judges each flow test.
