`/gaia-plan` splits a feature into phases. Each phase delivers one behavior from start to finish. Its tasks can run at the same time, and the types and interfaces the tasks share (the contracts) are fixed up front so the pieces fit together. It writes a plan folder, not code, and gives you a prompt to paste into a fresh session, where an orchestrator (the session that runs the plan) builds it.

The plan folder is saved in the [Notebook](/workflow/notebook/).

## When to use it

Use `/gaia-plan` when the work spans several files or modules, or has parts that can be built at the same time, such as UI, services, and tests. For a one-line fix or a single-file edit, just ask Claude.

When the goal is not settled yet, run [`/gaia-spec`](/workflow/spec/) instead. It plans its SPEC in the same session. See [Spec, plan, or just do it](/workflow/work-lifecycle/#spec-plan-or-just-do-it).

## How to invoke

```
/gaia-plan a feature description in plain language
```

From a saved SPEC:

```
/gaia-plan SPEC-005
```

With no description, `/gaia-plan` asks for one.

### Auto mode

```
/gaia-plan auto a feature description
```

Auto mode is for runs nobody is watching. It removes two questions:

- **Planner model.** On a model other than Opus or Fable, the planner uses Opus without asking.
- **Plan audit.** Clear fixes are applied without asking. A finding with more than one reasonable fix is written to `## Audit notes` in the plan's `README.md`. Read it before you paste the kickoff prompt.

A description is required. A description whose first word is "auto" is read as auto mode, so reword it.

## What gets produced

| Plan | Folder |
|---|---|
| From a SPEC | `.notebook/specs/SPEC-NNN/plan/` (a second plan for the same SPEC is `plan-2/`) |
| With no SPEC | `.notebook/plans/PLAN-NNN/` |

Inside it:

| File | Purpose |
| --- | --- |
| `README.md` | The overview: phase order, the tasks in each phase and their models, the shared contracts, and the source SPEC. |
| `ORCHESTRATOR.md` | The orchestrator's step-by-step instructions: where the work runs, phases and quality gates, sub-agent prompts, the audit before merge, git steps, and when to stop. |
| `KICKOFF.md` | The prompt a fresh session reads to start. |
| `task-<name>.md` | One per task: contracts, files to change, acceptance criteria, dependencies. |
| `PROGRESS.md` | Written during execution: one entry per completed or halted phase. |

## The flow

1. **Before it starts.** GAIA clears out [notebook entries it no longer needs](/workflow/notebook/#how-entries-are-cleared), and Claude offers to pull when your GAIA version is behind the remote, or stops until you push your local `main` when it has unpushed commits. See [Out-of-date or unpushed main](/reference/gates/#out-of-date-or-unpushed-main).
2. **Find the SPEC**, if you named one. If none matches, it stops instead of planning without it.
3. **Pick the planner model.** On Opus or Fable the planner uses your model. Otherwise Claude asks: Opus (recommended), Fable, or your current model. The planner runs at your session's `/effort`, so a higher effort drafts a deeper plan.
4. **Plan.** A planner sub-agent writes the folder.
5. **Verify.** A script checks that every required file is there. For a SPEC's plan, it also checks that each [critical flow](/workflow/spec/#critical-flows) belongs to exactly one task in the [closing flow-test phase](#flow-tests), that the task names the flow's test file at its expected path, and that the phase runs every flow test before it commits.
6. **Plan audit.** Reviewers check the plan before anything is built from it. See [The plan audit](#the-plan-audit).
7. **Report.** A [cost line](/models-and-context/cost/#what-you-see), then the prompt:

   ```text
   Read /absolute/path/to/plan/KICKOFF.md and execute it.
   ```

   Type `/clear` and paste it.

## The plan audit

The [SPEC audit](/workflow/spec/#the-spec-audit) checks what to build, and the [Code Audit Team](/workflow/code-audit-team/) checks the finished code. The plan audit checks what neither sees: how the work is split, which tasks run side by side, and the contracts between them. A flaw caught here costs one edit to the plan, not a failed run.

It runs on any plan with tasks running side by side, several phases, or a shared contract. A simple plan (one or two tasks, one phase, nothing shared) skips it. If your session cannot start sub-agents, it is skipped with a note.

### The lenses

Each lens is a fresh sub-agent that reads the plan and your code for itself:

| Lens | What it checks |
| --- | --- |
| (DP) Decomposition and dependencies | Side-by-side tasks that share state, edit the same files, need each other's output, or run project-wide checks (lint, type checks, Playwright, a dev server) that would collide. A phase order that ignores a real dependency. A contract two tasks read differently. Acceptance criteria that cannot be checked on their own. |
| (CG) Contract grounding | Every file path, export, type, and signature a task names really exists in your code and installed packages. |
| (COV) SPEC coverage | For a SPEC's plan only. Every flow and success criterion is covered, each flow has one task in the closing phase that names its test file, no build phase writes a flow test, no task contradicts the SPEC, and no task brings back work the SPEC ruled out. |

These checks have a clear yes-or-no answer against your code, so there is no refutation pass.

### What you see

Critical and major findings are printed as one list headed **Plan audit**, each with its evidence and recommended fix, then one question: **Accept all as recommended** or **Revise**. Minor findings are applied without asking.

A finding about one spot, such as a wrong contract, is fixed in the plan's files. A finding that the task split itself is wrong sends the plan back to the planner, and the rewritten plan is verified again (step 5).

## Execution

The orchestrator runs in the fresh session:

- **Where it runs** follows your team's [isolation policy](/workflow/work-lifecycle/#3-isolate): a separate worktree by default. The branch is `<type>/spec-<nnn>-<slug>` for a SPEC's plan or `<type>/plan-<nnn>-<slug>` otherwise, where `<type>` is the change's Conventional Commits type. The pull request title's type must match.
- **Each phase** hands its tasks to sub-agents, Sonnet by default. Sub-agents only edit files. Each one builds its task, writes only the tests [worth having](/workflow/testing/#what-gets-a-test) for it, and typechecks its own work before it returns. Every refusal, guard, or validation a task builds gets a test named in that task that makes it refuse, at the lowest layer that shows it (usually a route test), never left to a [flow test](#flow-tests). The phase gate runs typecheck, lint, and the existing tests, and the orchestrator commits each phase once it passes. See [Who does what](/workflow/work-lifecycle/#who-does-what).
- **A failed phase gate** gets one retry in these four cases. The one retry covers every failure in the gate.
  - A typecheck or lint error in files that each belong to one task. Each of those tasks gets its errors in a fresh sub-agent.
  - A [flow test](#flow-tests) that fails in the closing phase. It goes to a fresh sub-agent for the task that owns it, which may fix the code or the test, whichever is wrong.
  - A Playwright test that fails in a file that belongs to exactly one of the phase's tasks, when the test environment is not the cause. It goes to a fresh sub-agent for that task, which fixes the code, or updates the test when the phase changed that behavior on purpose.
  - A Playwright test from outside the phase that passed before and now fails, when the test environment is not the cause. It goes to the sub-agents whose app code the phase changed. They fix the code, or update the test when the phase changed that behavior on purpose.

  The gate then runs again. Any other failure, or a second failure in the same phase, stops the plan. A stop asks you one question, with **Stay halted** recommended, or **Discuss this** to talk it through.
- **A task that runs out of context** hands off to a fresh sub-agent. A task that would need a third handoff stops the plan and tells you.
- **The simplify pass** runs once, after the last phase commits. A sub-agent runs the `simplify` skill over the whole branch, and the orchestrator commits its edits through the [Quality Gate](/workflow/code-audit-team/#what-it-checks). If the gate fails or the pass stops partway, the edits are discarded and saved as a patch. Only a refused push or a failed discard stops the plan. The final summary says whether the pass applied, changed nothing, did not run, or was discarded, and where any patch is.
- **The pull request** opens as a draft after the first phase commits. After the simplify pass, the orchestrator runs the [checks on each flow test](#flow-tests) for a SPEC's plan, then the [worthiness step](/workflow/testing/#the-worthiness-step), the [overlap pass](/workflow/testing/#the-overlap-pass), and the wiki update, all before the [Code Audit Team](/workflow/code-audit-team/) reviews it. Once the team clears it, the orchestrator shows a summary and the cost of the implementation, then asks you before it merges, with holding the merge as the recommended answer.

### Resuming a plan

Running the kickoff again on a plan with completed phases shows each one with its commit and asks:

- **Resume** at the first incomplete phase
- **Restart from Phase 1**
- **Abandon**: stop without running, committing, merging, or deleting anything

When every phase is already complete, the run picks up at the simplify pass and skips any step that already finished.

If the working tree has uncommitted changes, the plan does not resume. It asks the same **Stay halted** or **Discuss this** question and never offers to stash, discard, or commit your changes.

A plan keeps the steps it was generated with, even after a GAIA update, until you regenerate it.

### Flow tests

A plan built from a SPEC ends with one closing phase after the build. It has one task per [critical flow](/workflow/spec/#critical-flows), each writing that flow's test, and no earlier phase writes one.

- **A web flow** gets one [Playwright](https://playwright.dev/) test at `apps/web/.playwright/flows/<name>.spec.ts`, where `<name>` is the flow's short name. A comment at its top, the `@covers` line, names the app folders the flow runs through.
- **A command-line flow** gets the test file the SPEC names.

Each flow test is one file. It walks the flow's journey through its happy path, plus only the effects that take several requests or sessions to set up, such as signing out ending a session or a role change applying to the next request. Where the SPEC requires the flow to work without JavaScript, it also posts the flow's forms to the server the way a browser without JavaScript would. It checks no page markup or ARIA attributes and repeats no refusal that a build task's test or another flow test already checks. The closing phase's gate runs every flow test before it commits.

After the last phase, GAIA checks each flow. Its test file must exist and have changed on the branch, and a SPEC or flow id such as `FLOW-001` must not appear in it. A web flow's test must also be one Playwright runs, with an `@covers` line that names every folder the SPEC lists for the flow and the branch changed. A failed check goes to the sub-agent for the task that owns that flow, for one round of fixes, and then the checks run again. A second failure, a failure no task owns, or a check that cannot run stops the plan with the same **Stay halted** or **Discuss this** question.

The [worthiness review](/workflow/testing/#the-worthiness-review) then judges each flow test against its flow.
