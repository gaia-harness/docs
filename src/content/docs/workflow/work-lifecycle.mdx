Every task follows one lifecycle, whether a command drives it (`/gaia-plan`, `/gaia-debt`, a maintenance command) or you just asked for a fix:

1. **Claim** the GitHub issue you're working on, if there is one, so nobody else starts it.
2. **Name** the branch.
3. **Isolate** the work in its own git worktree or a feature branch, per your team's policy, so tasks running at the same time never overwrite each other's changes.
4. **Commit** through the Quality Gate and the commit hooks, and open a **draft** pull request.
5. **Audit** the pull request with the [Code Audit Team](/workflow/code-audit-team/).
6. **Merge.** Ad-hoc work waits until you ask. [Some commands](#6-merge) merge their own pull request.
7. **Clean up** the worktree and branch, and pull the latest `main`.

Every task gets a draft pull request, even when you did not ask for one. If you say you will review or commit an edit yourself, GAIA leaves it uncommitted on your current branch and none of these steps apply.

### Spec, plan, or just do it

When you ask for work without naming a command, GAIA first checks whether it deserves a spec or a plan, and asks when it does:

- A new feature that adds user-visible rules, data, or flows gets a recommendation for [`/gaia-spec`](/workflow/spec/), even when your request is long and detailed. A SPEC turns those rules into checked acceptance tests.
- Clear internal work worth planning first gets a recommendation for [`/gaia-plan`](/workflow/plan/): several phases, parallel streams, a rollout across many files, or a migration of stored data.
- A bug fix or a small contained change proceeds with no question.

You can choose the recommended approach, or `Just do it`, which goes straight to step 1. GAIA asks once per task, and not at all if you already said how to proceed ("just fix it"), the work's branch already exists, or a GAIA command is running.

## Who does what

When a task is big enough to hand off, GAIA splits it across sub-agents: separate Claude instances, each with a fresh context, that report back to your session. Each gets one role:

| Role | Who | What it does |
|---|---|---|
| Advisor | A read-only sub-agent | Investigates and writes its findings to a file. |
| Decider | Your session | Reads the findings, decides what to do, and asks you when the choice is yours. |
| Executor | A sub-agent | Edits files, and nothing else. |
| Verifier | A check after the executors | Compares the changes with the plan before anything is committed. |

Sub-agents never commit, push, or create branches. Your session does that, and runs the [Quality Gate](/workflow/code-audit-team/#quality-gate) once per commit, after the verifier passes.

**Why:**

- Wide reading happens in the advisors, so your session's context holds the decision instead of the search.
- Executors share one working copy, so one executor's git command could discard another's unsaved edits.
- One gate per commit avoids paying for a slow check several times on half-finished work.

Some work never leaves your session at all. See [How GAIA picks a model](/models-and-context/model-choice/#how-gaia-picks-a-model). A command with its own steps follows them where they differ: a [`/gaia-plan` run](/workflow/plan/#execution) commits once per phase, and the [audit loop](/workflow/code-audit-team/#the-audit-loop) commits its own fix rounds.

## 1. Claim

Work with no issue behind it, such as a quick fix you asked for, skips this step.

GAIA reads the issue's labels first. If it is labeled `in-progress`, it's already being worked on, so GAIA tells you and doesn't start. Otherwise it adds the `in-progress` label.

GAIA removes the `in-progress` label when it merges the pull request, or when the work is dropped.

**Why:** two agents or people starting the same issue do the work twice, and the two versions conflict at merge. See the [gate reference](/reference/gates/#issue-claim).

A `tech-debt` issue is claimed by [`/gaia-debt <n>`](/workflow/debt/), never by hand.

## 2. Name

GAIA generates every branch name, in the form `<kind>/<rest>`:

| Work | Branch |
|---|---|
| Ad-hoc work | `<type>/[<issue>-]<slug>`, for example `fix/142-login-redirect` |
| A plan from a SPEC | `<type>/spec-<nnn>-<slug>` |
| A plan with no SPEC | `<type>/plan-<nnn>-<slug>` |
| A tech-debt fix (`/gaia-debt`) | `debt/<n>-<slug>`, or `debt/<a>-<b>-batch` for a batch |
| Maintenance commands | `deps/`, `update/`, `wiki/`, `cleanse/`, `codify/`, `fitness/`, or `residue/` plus a timestamp |

`<type>` is the [Conventional Commits](https://www.conventionalcommits.org/) type (`feat`, `fix`, `chore`, and the rest), the same one the pull request title uses. See [Git hooks and conventions](/workflow/git-conventions/).

**Why:** GAIA reads branch names back to find its own work, so a resumed plan or `/gaia-debt` knows which issue or SPEC a branch belongs to.

## 3. Isolate

### Why GAIA works in worktrees

A [git worktree](https://git-scm.com/docs/git-worktree) is a second working copy of the same repository, in its own folder and on its own branch. By default, GAIA gives every task its own worktree (see [Isolation policy](#isolation-policy)), so:

- **Tasks run side by side.** A plan, a bug fix, and a dependency update can each run in their own session at once, without overwriting each other's changes.
- **No stashing or branch switching.** Starting a task in the main checkout means stashing changes or switching branches, which is how work gets lost or lands on the wrong branch. A worktree needs neither.
- **Each worktree sets itself up**, installing dependencies and taking its own ports, so Claude can run the app and tests there right away. See [Worktrees provision themselves](#worktrees-provision-themselves).

[Maintenance commands](/maintenance/#how-maintenance-commands-run) start from the main checkout and isolate their own work.

### Isolation policy

Your team's policy is `isolation_policy` in `.gaia/project.json`:

| Policy | What happens |
|---|---|
| `always-worktree` (default) | Every task gets its own worktree, without asking. |
| `prefer-worktree` | GAIA suggests a worktree, and you can choose a branch instead. |
| `prefer-branch` | GAIA suggests a feature branch in your checkout, and you can choose a worktree instead. |

A repo admin changes it with `/setup-gaia --reconfigure`. Saying "in a worktree" or "on a branch" in your request answers the question up front, though under `always-worktree` a request for a branch still gets a worktree.

<Aside type="note" title="Already on a feature branch? New work gets a worktree">
GAIA offers the worktree-or-branch choice only when the main checkout is on `main`. If it is on another branch, that branch already holds other work, so a new task always gets its own worktree to keep the two apart.
</Aside>

<Aside type="caution">
If the main checkout already has uncommitted changes for the task, GAIA copies them into the new worktree so the task starts with them. The main checkout keeps its copy too.
</Aside>

### Worktrees provision themselves

GAIA uses Claude Code's built-in worktrees under `.claude/worktrees/`. When a session enters one, GAIA names its branch and sets it up:

- **Shared state is linked, not copied.** GAIA's machine-local state (`.gaia/local`), the [Notebook](/workflow/notebook/), and your `.env` files are linked from the main checkout. Nothing is lost when the worktree is removed, and your secrets stay in one file.
- **Dependencies install in the background**, along with React Router's [route types](https://reactrouter.com/explanation/type-safety), so the session does not wait.
- **Each checkout has its own ports.** See [Ports per worktree](#ports-per-worktree).
- **Edits stay in the right copy.** If Claude aims an edit at the main checkout from inside a worktree, GAIA sends it back and Claude redoes it in the worktree ([why](/reference/gates/#worktree-path-mismatch)).

In the rare case a worktree's links break, ask Claude:

```text
This worktree's GAIA links are broken. Repair them.
```

What a worktree holds, next to the main checkout:

<FileTree>
- my-app/ the main checkout
  - .gaia/
    - local/ GAIA's machine-local state, the only copy
  - .notebook/ the only copy
  - apps/
    - web/
      - .env your secrets, the only copy
  - .claude/
    - worktrees/
      - my-task/ one worktree
        - .gaia/
          - local/ a link to the main checkout's copy
        - .notebook/ a link
        - node_modules/ its own install
        - apps/
          - web/
            - .env a link
            - node_modules/ its own install
            - .gaia-ports this worktree's ports, for example 5174 and 6007
</FileTree>

### Ports per worktree

Every worktree gets its own ports for the app's dev server, [Storybook](https://storybook.js.org/), and [Playwright](https://playwright.dev/), so the app can run in several worktrees at once.

- **The main checkout keeps the defaults:** 5173 (dev server) and 6006 (Storybook).
- **Each worktree gets a numbered slot**, the lowest one free, and keeps it. Its ports are the defaults plus the slot number: slot 1 is 5174 and 6007. Slots cover the web app only, and are shared across all your GAIA projects on this machine.
- **`pnpm dev`, `pnpm storybook`, and `pnpm pw` use the worktree's ports automatically.** To see them, ask Claude: `Which ports does this worktree use?`
- **A taken port stops the server instead of switching it**, so you never test another checkout's server by mistake. Start Storybook with `pnpm storybook`, not `storybook dev`, which skips this check.
- **Orphaned servers are stopped for you.** At session start, GAIA stops any server whose Claude session has ended or whose worktree was removed. A server you started yourself is never stopped automatically.

## 4. Commit and open the draft pull request

Every commit passes the commit hooks, and one that touches source or build configuration also passes the [Quality Gate](/workflow/code-audit-team/#quality-gate). The pull request opens as a draft with a Conventional Commits title. `Closes #<n>` goes in the pull request body, never in a commit message, because a squash merge copies commit messages into the final commit and GitHub would close the issue from there.

<Aside type="note" title="Why draft?">
A draft tells reviewers the pull request is still in progress. GAIA marks it ready for review once the audit passes. See the [gate reference](/reference/gates/#draft-pull-requests).
</Aside>

## 5. Audit

GAIA audits every pull request before merge, including small one-off changes, though a small change can get a [light review](/workflow/code-audit-team/#light-review). Before the first round, GAIA runs the [worthiness step](/workflow/tdd/#the-worthiness-step) on tests that need it. See [Code Audit Team](/workflow/code-audit-team/).

For ad-hoc work you did not ask to merge, GAIA stops here and reports the pull request as ready to merge.

## 6. Merge

Who decides when to merge depends on what started the work:

| Work | When it merges |
|---|---|
| Ad-hoc work (a plain request) | Only when you ask. A later message asking to merge counts. |
| A plan run from its kickoff prompt | At the end, GAIA prints a summary and asks whether to merge or hold. |
| [`/gaia-debt`](/workflow/debt/), [`/gaia-wiki`](/maintenance/wiki/), [`/update-deps`](/maintenance/update-deps/), [`/gaia-cleanse`](/maintenance/cleanse/) | As part of the run, once the audit passes and the required checks are green. |
| [`/gaia-residue`](/maintenance/residue/), [`/gaia-codify`](/maintenance/codify/), [`/gaia-fitness`](/maintenance/fitness/) | The command asks first, and you can leave the pull request open. |
| [`/update-gaia`](/maintenance/update-gaia/) | It opens a draft pull request and stops. You merge it when you are ready. |

GAIA squash-merges through GitHub's auto-merge, which completes once the required checks pass. With auto-merge off (see [`/setup-gaia`](/getting-started/setup-gaia/#recommended-defaults-admin-only)), GAIA waits for the required checks itself, then merges. Either way it stops as soon as a check fails or the pull request has a conflict, and cleans up only after the merge lands.

## 7. Clean up

After the merge, GAIA removes the worktree (or switches off the feature branch), deletes the local branch, and pulls `main`, reinstalling dependencies only when the lockfile changed.

Cleanup never forces a pull and never stashes. A worktree with uncommitted files or unpushed commits is kept, and GAIA tells you what is left. Kept worktrees whose work is merged are listed at every session start, and Claude removes one only when you name it.

## Resuming long work

Work that spans sessions resumes from a small saved state: a plan's progress files, `/gaia-spec`'s draft, or a `STATE.md` under `.gaia/local/runs/`. A resumed session reads that state and the files it lists, and nothing else.

When the context reaches GAIA's [red band](/models-and-context/token-efficiency/#context-bands), GAIA finishes the current step, saves your place, and asks:

- **Continue here**: keep working until the next band.
- **Clear and resume**: GAIA prints a continuation prompt. Run `/clear` and paste it.

You can also ask for a continuation prompt at any time.
