`/gaia-spec` turns a feature idea into a SPEC through a guided conversation. A SPEC is a written description of what to build and how to test it, locked once saved. GAIA then plans it in the same session with [`/gaia-plan`](/workflow/plan/) and stops at the plan's KICKOFF prompt. The building starts in a fresh session.

The SPEC and its plan are saved in the [Notebook](/workflow/notebook/).

## When to use it

Use `/gaia-spec` when the scope is not clear yet, or when a new feature adds user-visible rules, data, or flows, however well you have described it: the SPEC turns those rules into checked acceptance tests.

For a bug fix, a refactor, or a copy edit, just ask Claude, or go straight to [`/gaia-plan`](/workflow/plan/). See [Spec, plan, or just do it](/workflow/work-lifecycle/#spec-plan-or-just-do-it).

## How to invoke

```
/gaia-spec your feature description
```

Claude asks you questions to settle what you want. A question with fixed answers is a menu, recommended option first, with **Discuss this** to talk it through.

### Auto mode

```
/gaia-spec auto your feature description
```

Claude answers its own questions with the recommended option, checks both gates itself, and plans with [`/gaia-plan auto`](/workflow/plan/#auto-mode), so the run finishes without asking you anything. It always starts a new SPEC and skips the model check. Anything it could not settle is saved as an open question for you to review.

Use it when your description is already complete. A description whose first word is "auto" is read as auto mode, so reword it.

## What gets produced

Everything lands in `.notebook/specs/SPEC-NNN/`:

| File | Purpose |
| --- | --- |
| `SPEC.md` | The locked SPEC: intent, success criteria, UATs, scope rules (always, ask first, never), and the decisions settled along the way with their reasons. |
| `AUDIT.md` | The [SPEC audit](#the-spec-audit)'s report: instructions the plan must follow, fixes folded into the SPEC, and findings that were disproved. |
| `plan/` | The plan, written by [`/gaia-plan`](/workflow/plan/#what-gets-produced). |

Each SPEC number is reserved by pushing a `spec/NNN` git tag, so teammates never get the same number. See [Numbers do not travel](/workflow/notebook/#why-it-stays-on-your-machine) for a repository with no remote.

### UATs

A UAT (user acceptance test) is an automated acceptance test written into the SPEC. Each one has three parts:

- **Given**: the starting state
- **When**: one action, by the user or the system
- **Then**: an outcome a test can check

Once the SPEC is saved, the UATs are the contract. [`/gaia-plan`](/workflow/plan/#uat-specs) turns them into tests, and changing one means [reopening the SPEC](#reopening-a-saved-spec).

## Before it starts

- **Model check.** The SPEC is written on your session's model. On a model other than Opus or Fable, Claude offers to stop so you can switch with `/model`.
- **Pull check.** When the remote has a newer GAIA version than your checkout, Claude offers to pull first.
- **Resume.** When an unfinished draft exists, you choose to resume it or start new. A draft another open session is still writing is never offered.

GAIA also clears out [notebook entries it no longer needs](/workflow/notebook/#how-entries-are-cleared).

## The flow

1. **Draft.** Claude reserves the SPEC number and writes a first draft.
2. **Gate 1: shape.** Before asking anything, Claude shows in plain language what it thinks you want, with every proposed UAT. You confirm or revise. Later steps check the SPEC against what you confirmed here.
3. **Questions.** One at a time, each built on your last answer, until every topic is settled or after 10 questions (5 in auto mode). When Claude needs facts, it researches them itself.
4. **Self-review.** A sub-agent checks that the draft matches gate 1 and does not contradict itself. It also flags UATs that need a browser, walk one user flow, and differ only in the step they exercise, and recommends folding them into one browser journey, with each rule kept as its own UAT. It also recommends splitting an access refusal out of a browser journey into its own UAT. It fixes minor problems. Critical and major ones come to you as one list with recommended fixes: accept all, or revise the ones you name.
5. **SPEC audit.** Independent reviewers check the draft against your code. See [The SPEC audit](#the-spec-audit).
6. **Gate 2: the brief.** Claude shows what the SPEC changes, why, what success looks like, every UAT, what the plan will do because of the audit, the costs and risks you accept, and anything still open. Revise until it is right.
7. **Save.** The SPEC is saved and locked.
8. **Plan.** GAIA runs `/gaia-plan` on the SPEC in the same session. The run ends with a [cost box](/models-and-context/cost/) and the KICKOFF prompt to paste into a fresh session.

<Aside type="caution">
Confirming gate 2 locks the SPEC. Changing it later means reopening it with a written reason. Get it right before you confirm.
</Aside>

### Reopening a saved SPEC

When a plan stops because a UAT can no longer hold, type:

```
/gaia-spec reopen SPEC-<NNN>
```

Claude asks why the UAT cannot hold, proposes the new UAT and any plan change that follows, and asks you to confirm. It records your reason and the old UAT in the SPEC, offers to discard the stopped phase's unfinished edits, and gives you the plan's KICKOFF prompt to paste into a fresh session.

## The SPEC audit

Before gate 2, a team of sub-agents reviews the draft. Each one reads your code for itself, so the SPEC is checked against what is really there, not what the conversation assumed. It runs on every SPEC.

A low-stakes, narrow SPEC gets the **Standard** audit. A high-stakes one, or one that touches security or a data migration, gets the **Deep** audit.

### The lenses

Each reviewer looks through one lens. Its short code, such as `COV`, appears in each finding's id. Four lenses run on every SPEC:

| Lens | What it checks |
| --- | --- |
| (FG) Factual grounding | Every claim about your code, dependencies, file paths, and conventions is true. A new dependency is justified and pinned. |
| (TST) UAT testability | Each UAT can fail: no way to pass while the feature is broken. |
| (COV) Coverage and consistency | Every success criterion and promise has a UAT, the scope rules agree with the UATs, and the SPEC follows your conventions. |
| (RT) Red team and feasibility | A way every UAT passes yet the feature is not delivered, a check that cannot run, a missed file or caller, an assumption the plan would take as fact. |

Specialist lenses join when the draft touches their area:

| Lens | Joins when the SPEC touches |
| --- | --- |
| (SEC) Security | Sign-in, tokens or secrets, redirects, uploads, permissions, personal data, raw user input, headers, cookies |
| (MIG) Migration | Data formats or schemas, renamed or removed fields, breaking API changes |
| (A11Y) Accessibility | Anything that renders on screen |
| (DOC) Documentation | Wiki or docs deliverables |
| (PERF) Performance | Data volume, loops over collections, network calls, caching, rendering |

### Refutation

A separate reviewer tries to disprove each critical or major finding, and drops it unless the problem shows in the code or the draft. On the Deep audit, three reviewers try, and the finding stays only if two of them fail. A completeness reviewer then looks for what every lens missed.

With more than 24 critical or major findings on Standard, or more than 8 on Deep, one reviewer per lens checks all of that lens's findings instead, and the completeness review is skipped. This keeps the audit's cost from growing with the number of findings.

### Findings that survive

- **The SPEC is wrong** (a UAT that could pass on broken code, a missing UAT, a wrong intent): the fix goes into the draft. Critical and major fixes come to you as one list. Minor ones are folded in.
- **The SPEC is right, but the build needs steering** (for example, a file the change must also update): it becomes an instruction in `AUDIT.md` that the plan must follow.

In auto mode, a clear fix is applied, and a finding with more than one reasonable fix is left open for you.

If your session cannot start sub-agents, the audit is skipped and gate 2's brief says so.

## While it runs

- **It writes only to the notebook and GAIA's local files**, never your source code, so you can keep working in other sessions, on a branch or in a [worktree](/workflow/work-lifecycle/#3-isolate).
- **Project decisions go into the SPEC, the wiki, or `.claude/rules/`**, never into machine-local memory.
- **Progress is saved after every answer.** To stop, type a save request (such as "save partial") into a question's **Other** answer, or ask from **Discuss this**. The next `/gaia-spec` offers to resume.
- **Long sessions** pause at the context red band like any other. See [Work lifecycle](/workflow/work-lifecycle/#resuming-long-work).
