`/gaia-spec` turns a feature idea into a SPEC through a guided conversation. A SPEC is a written description of what to build, with every rule stated case by case, locked once saved. GAIA then plans it in the same session with [`/gaia-plan`](/workflow/plan/), offers the [test stage](/workflow/test-stage/) that decides its tests, and stops at the plan's KICKOFF prompt. The building starts in a fresh session.

The SPEC and its plan are saved in the [Notebook](/workflow/notebook/).

## When to use it

Use `/gaia-spec` when the scope is not clear yet, or when a new feature adds user-visible rules, data, or flows, however well you have described it: the SPEC names the flows that must not break, and each one gets a test.

For a bug fix, a refactor, or a copy edit, just ask Claude, or go straight to [`/gaia-plan`](/workflow/plan/). See [Spec, plan, or just do it](/workflow/work-lifecycle/#spec-plan-or-just-do-it).

## How to invoke

```
/gaia-spec your feature description
```

Claude asks you questions to settle what you want. A question with fixed answers is a menu, recommended option first, with **Discuss this** to talk it through.

### Auto mode

```
/gaia-spec auto your feature description
```

Claude answers its own questions, checks both gates itself, and plans with [`/gaia-plan auto`](/workflow/plan/#auto-mode), test stage included, so the run finishes without asking you anything. It always starts a new SPEC and skips the model check. Anything it could not settle is saved as an open question for you to review.

Use it when your description is already complete. A description whose first word is "auto" is read as auto mode, so reword it.

## What gets produced

Everything lands in `.notebook/specs/SPEC-NNN/`:

| File | Purpose |
| --- | --- |
| `SPEC.md` | The locked SPEC: intent, success criteria, [critical flows](#critical-flows), [behaviors](#behaviors), scope rules (always, ask first, never), and the decisions settled along the way with their reasons. |
| `REQUIREMENTS.md` | Your description and every question and answer, word for word. Every later step reads it as what you asked for, and nothing edits it. |
| `AUDIT.md` | The [SPEC review](#the-spec-review)'s report: instructions the plan must follow, the fixes made to the draft, and what the review decided about each critical finding. |
| `plan/` | The plan, written by [`/gaia-plan`](/workflow/plan/#what-gets-produced). |

Each SPEC number is reserved by pushing a `spec/NNN` git tag, so teammates never get the same number. See [Numbers do not travel](/workflow/notebook/#why-it-stays-on-your-machine) for a repository with no remote.

### Critical flows

A critical flow is a path through the feature that, if it broke, would block a user's main task or put data, money, or security at risk. A SPEC has as many as the feature needs, with no set number. Each flow has an id such as `FLOW-001`, a short kebab-case name that becomes its test's file name, a one-line title, and why it is critical. A web flow also lists the app folders it covers. A command-line flow names its test file instead.

A flow names a path, never a list of cases. The rules the feature must follow go in its behaviors.

Once the SPEC is saved, the [test stage](/workflow/test-stage/) gives every flow one test, written in a closing phase after the build (see [Flow tests](/workflow/plan/#flow-tests)), unless you [skip it](/workflow/test-stage/#skipping-it).

### Behaviors

The `## Behaviors` section states every rule the feature has, error cases, refusals, and security rules included. Each behavior has an id that never changes, one kind, and its cases. Each case names who acts, the state, the input, and the outcome by value: a status, a message, a redirect, or the exact text shown, never "an error".

```markdown
- **B1** (access): Only the order's owner can open its receipt page.
  - Case: a signed-in user who owns order 7, opening /orders/7/receipt -> the page shows "Receipt for order 7".
  - Case: a signed-in user who does not own order 7, opening /orders/7/receipt -> 403 and the text "You cannot view this order".
```

The kind is `access`, `forgery`, `secret`, `refusal`, `data-loss`, or `other`. The first three are [security kinds](/workflow/testing/#security-tests), and their tests are written by a separate sub-agent. Where your description already lists values, such as a table of actions or a set of labels, the SPEC points to that part of `REQUIREMENTS.md` instead of copying it.

The SPEC plans no tests. The [test stage](/workflow/test-stage/) reads the behaviors and decides how each is proven.

## Before it starts

- **Model check.** The SPEC is written on your session's model. On a model other than Opus or Fable, Claude offers to stop so you can switch with `/model`.
- **Pull check.** When the remote has a newer GAIA version than your checkout, Claude offers to pull first. When your local `main` has unpushed commits, it stops until you push them. See [Out-of-date or unpushed main](/reference/gates/#out-of-date-or-unpushed-main).
- **Resume.** When an unfinished draft exists, you choose to resume it or start new. A draft another open session is still writing is never offered.

GAIA also clears out [notebook entries it no longer needs](/workflow/notebook/#how-entries-are-cleared).

## The flow

1. **Gate 1: shape.** GAIA reserves the SPEC number. Before asking anything, it shows in plain language what it thinks you want and proposes the critical flows, with its recommended set marked. You confirm, or drop, add, or edit flows.
2. **Questions.** One at a time, each built on your last answer, until every topic is settled or after 10 questions (5 in auto mode). When Claude needs facts, it researches them itself.
3. **Requirements.** Your description and every question and answer are saved, word for word, to `REQUIREMENTS.md`.
4. **Draft.** Claude writes the whole SPEC in one pass, stating every behavior with its cases. A question still open is settled now or left open with a reason. In an interactive run, Claude asks you about each one.
5. **Review.** Independent reviewers check the draft, and one sub-agent applies their findings. See [The SPEC review](#the-spec-review).
6. **Gate 2: the brief.** Claude shows what the SPEC changes, why, what success looks like, every flow with the folders it covers or its test file, what the plan will do because of the review, the costs and risks you accept, and anything still open. Revise until it is right.
7. **Save.** The SPEC is saved and locked.
8. **Plan.** GAIA runs `/gaia-plan` on the SPEC in the same session, then offers its test stage. The run ends with a [cost box](/models-and-context/cost/) and the KICKOFF prompt to paste into a fresh session.

<Aside type="caution">
Confirming gate 2 locks the SPEC, and nothing edits it after that. Get it right before you confirm.
</Aside>

## The SPEC review

Before gate 2, a team of sub-agents reviews the draft, all at once. Each one reads your code for itself, so the SPEC is checked against what is really there, not what the conversation assumed. It runs on every SPEC.

### The lenses

Each reviewer looks through one lens. Its short code, such as `COV`, appears in each finding's id. Five lenses run on every SPEC:

| Lens | What it checks |
| --- | --- |
| (TST) Testability | Each behavior, flow, and success criterion can fail, with no way to pass while the feature is broken. Each behavior states its cases clearly enough to write a test from the text alone, never by example or "etc.". In every behavior it looks for three gaps. One is what happens when a value the user sends is forged or edited. One is the form the user sees for a stored value, such as a date or a status. One is what is left when an operation that makes several writes fails partway. |
| (COV) Coverage and consistency | Every promise in the intent has a flow, no critical flow is missing, the scope rules agree with the flows, no flow needs a control, step, or value the SPEC's own rules allow only in another state, every requirement in `REQUIREMENTS.md` reaches a behavior, and the SPEC follows your conventions. |
| (SEC) Security | Injection, server-side request forgery, open redirects, leaked tokens or secrets, missing authorization, and unsafe deserialization. A credential the app holds for another service needs a rule keeping it out of the browser, and a signed-only cookie does not do that. For every grant, it checks the SPEC says who is refused. |
| (BRIEF-FIT) Brief fit | Checks the draft against your description, never the other way around. It flags a decision or default your description contradicts, access the draft gives to someone your description does not name, scope you did not ask for, and anything you said that the draft drops or changes. When you list who may do something, everyone else is refused. |
| (FG) Factual grounding | Every claim about your code, dependencies, file paths, and conventions is true. A new dependency is justified and pinned. |

Specialist lenses join when the draft touches their area:

| Lens | Joins when the SPEC touches |
| --- | --- |
| (MIG) Migration | Data formats or schemas, renamed or removed fields, breaking API changes |
| (A11Y) Accessibility | Anything that renders on screen |
| (DOC) Documentation | Wiki or docs deliverables |
| (PERF) Performance | Data volume, loops over collections, network calls, caching, rendering |

### Critical findings

When any lens raises a critical finding, one more sub-agent tries to disprove the critical findings, without asking you anything. It drops a finding only when every gap the finding names turns out to be wrong, and lowers one whose harm is overstated. A finding that a value the app must keep on the server has no rule keeping it there is never dropped, or lowered below major, because of who owns the value or a cookie setting. Major and minor findings go straight to the fixer.

### The fixer

One sub-agent applies every finding that stands:

- **The SPEC is wrong** (a behavior, flow, or success criterion is wrong, can pass on broken code, or is missing): the fix goes into the draft as a behavior, such as a rule, a refusal, or an error state. A fix never adds a test.
- **The SPEC is right, but the build needs steering** (for example, a file the change must also update): it becomes an instruction in `AUDIT.md` that the plan must follow. It states what the code must meet, never which test to write.

When two findings conflict, the more severe one wins. When your description can be read two ways, the fixer takes the narrower reading of who may do what and marks it as an assumption in the SPEC.

A fix that removes, narrows, or rewrites a behavior must say where each case it removed now lives in the SPEC: still stated, restored, turned into a refusal, moved out of scope, corrected, or left open. A script checks each answer against the draft and sends back a fix that loses a case without one. Security and refusal behaviors are stricter. A case of an access, forgery, secret, or refusal behavior can only stay stated, be restored, become a narrower refusal, or be left open. If the fix is sent back twice, its lost cases are saved as open questions, shown at gate 2 under **Not settled**.

You see the result at gate 2. If your session cannot start sub-agents, the review is skipped and gate 2's brief says so.

## While it runs

- **It writes only to the notebook and GAIA's local files**, never your source code, so you can keep working in other sessions, on a branch or in a [worktree](/workflow/work-lifecycle/#3-isolate).
- **Project decisions go into the SPEC, the wiki, or `.claude/rules/`**, never into machine-local memory.
- **Progress is saved after every answer.** To stop, type a save request (such as "save partial") into a question's **Other** answer, or ask from **Discuss this**. The next `/gaia-spec` offers to resume.
- **Long sessions** pause at the context red band like any other. See [Work lifecycle](/workflow/work-lifecycle/#resuming-long-work).
