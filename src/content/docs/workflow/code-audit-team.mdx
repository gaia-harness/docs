Every change in a GAIA project is checked twice: the [Quality Gate](#quality-gate) runs before each commit, and the Code Audit Team reviews the pull request before it merges.

The audit is a team of reviewers (members). Each member is a Claude sub-agent responsible for a set of your files, and a pull request is reviewed by every member whose files it changes. The audit runs in your Claude Code session, not on [GitHub Actions](https://docs.github.com/en/actions) ([why](#why-the-audit-runs-locally)).

GAIA's merge hook keeps Claude from merging until every member whose files changed has approved. The `GAIA-Audit` required check covers the merge button on github.com: a pull request merged there waits until the audit has run.

## Quality Gate

The Quality Gate is the full set of checks GAIA runs before Claude commits source code. The [pre-commit hook](/workflow/git-conventions/#native-git-hooks) checks only the staged files. The gate checks every package in your workspace, so it also catches what a change breaks elsewhere.

### When it runs

Before any commit that stages source code (`.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`, or `.css`) or a config that changes what the checks do: `package.json`, the lockfile, and the [TypeScript](https://www.typescriptlang.org/), [Vite](https://vite.dev/), [Vitest](https://vitest.dev/), [Playwright](https://playwright.dev/), and [ESLint](https://eslint.org/) configs. A commit of only Markdown, `.claude/` files, wiki pages, or images skips it.

### What it checks

| Step | Passes when |
|---|---|
| Simplify | Claude has run the `simplify` skill on the change and applied what it recommends. A plan's commits and an audit fix round's commit skip this step. A plan makes [one pass over the whole branch](/workflow/plan/#execution) after its last phase instead. |
| Localization | No user-facing text is hardcoded, and no translation key is missing its value. |
| Typecheck (`pnpm typecheck`) | Zero errors. |
| Lint (`pnpm lint`) | Zero errors and zero warnings. Lint also fixes formatting, because [Prettier](https://prettier.io/) runs as an ESLint rule. |
| Unit tests (`pnpm test:ci`) | Every test passes with zero console warnings, in every package. Stories and hook tests run in headless Chromium. |
| End-to-end tests (`pnpm pw`) | Every Playwright test passes. |
| Dev server | This checkout's dev server starts and its home page answers with HTTP 200. A home page that redirects within the app, such as to a login page, passes when the page it lands on answers 200. GAIA first stops a dev server that Claude's own session left running on the port, even after `/clear`. When anything else holds the port, Claude asks: **Hold the commit** (recommended, since it may be another session's server) or **Stop it**. |
| Build (`pnpm build`) | The production build succeeds. |

Claude fixes every warning, not only errors, then shows you the results and asks whether to commit or hold the change. A workflow that commits on its own (an audit fix round, [`/gaia-debt`](/workflow/debt/), a plan's phases, [`/gaia-init`](/getting-started/gaia-init/)'s first commit) commits a clean gate without asking. Each has its own point where you review, and init's commit holds only the new project GAIA set up. An audit fix round with only Minor, non-security fixes skips the end-to-end tests, dev server, and build; those run once on the finished change before `GAIA-Audit` is posted.

Type checking, linting, and unit tests run in every package with a `typecheck`, `lint`, or `test:ci` script, so a package you add, such as a backend, joins the gate through its own scripts ([The backend is left to you](/getting-started/project-layout/#the-backend-is-left-to-you)). Claude warns about a package with tests but no `test:ci` script, or TypeScript but no `typecheck` script. The end-to-end, dev server, and build steps check the web app only.

## Members

The list of members (the roster) lives in `.gaia/audit-ci.yml` under `auditors:`. Each entry assigns file patterns (globs) to a member. To change it, ask Claude ([Covering new code](#covering-new-code)). Three members ship:

| Member | Owns | Reviews for |
|---|---|---|
| `code-audit-frontend` (the default member) | Every package under `apps/` and `packages/`: the app, its tests, Storybook and Playwright setup, manifests, lockfile, build and lint configs, `apps/web/.claude/**`, and root tooling such as `.npmrc` | Security, performance, fit with your architecture, edge cases, accessibility, and maintainability: what takes understanding the code, beyond lint and types. Library rules load from `apps/web/.claude/agents/code-audit-frontend/` ([Library rules](#library-rules-for-code-audit-frontend)). |
| `code-audit-github-workflows` | `.github/workflows/*.yml` and `.github/actions/**/*.yml` | Unsafe third-party actions, script injection, too-broad permissions, and mishandled secrets. |
| `code-audit-shell` | Every shell script and [bats](https://github.com/bats-core/bats-core) test (`**/*.sh`, `**/*.bats`), `.claude/hooks/**`, `.githooks/**`, and the root `.claude/settings.json` | Unquoted variables, silent failures, a guard that allows when it should block, and scripts that break on macOS's older bash, `sed`, or `date`. Hooks that read input unsafely or can break your session. bats assertions that can never fail. In `.claude/settings.json`, every hook or permission rule the change removes or weakens, listed for you to read before you approve the merge. |

Each file goes to the first member whose pattern matches, with the default member last. So a shell script under `apps/web/` belongs to `code-audit-shell`.

`code-audit-shell` skips GAIA's own shell files when the change is a GAIA update, but never skips `.claude/settings.json`, which you are expected to customize.

`code-audit-frontend` also runs three tools and lists their findings as advice that never blocks approval: [React Doctor](https://github.com/millionco/react-doctor) when the change touches a `.ts` or `.tsx` file, [Knip](https://knip.dev/) (unused files, exports, and dependencies) when it touches one of those, a `package.json`, or the lockfile, and a dependency security advisory check on every review.

Members only report. A separate fixer makes the repairs, and a script checks each repair before it is kept. A repair that adds a guard, refusal, or validation also adds a test that makes it refuse, unless no test can reach it, which the fixer then reports. The fixer adds such a rule only when the SPEC, a decision page in the wiki, or your existing code or docs already call for it. A rule that only a finding proposes stays open, and the [branch checkpoint](#the-branch-checkpoint) asks you what to do with it, such as filing it or stating it as a requirement.

### Covering new code

`code-audit-frontend` already covers every package under `apps/` and `packages/`. On a package that is not a React app, it skips its React, accessibility, and translation checks and keeps the rest, security included. When you add code in another language, such as a backend, choose:

- **Give it its own member** (better for another language or stack): a [Claude Code sub-agent](https://code.claude.com/docs/en/sub-agents) file in `.claude/agents/` saying what to review for, plus a roster entry with its name and file patterns. See [Adding a member](#adding-a-member).
- **Add its patterns to an existing member** whose review fits.

A file no member covers still goes to `code-audit-frontend`, so it is reviewed, but by a reviewer written for a React app. Only a pull request whose every file is outside the audit's scope (wiki pages, the root `.claude/` folder, GAIA's `.gaia/` files, `docs/`, and root Markdown) merges with no member's review. A shell script or hook in those folders still goes to `code-audit-shell`.

### Adding a member

Give Claude a prompt like this, with your own folder and stack:

```text
Add a Code Audit Team member for the Python API in backend/. Follow the wiki page "Registering a Code Audit Team Member": start from a copy of the workflows member, name it code-audit-python, write its review guidance for Python and FastAPI, add its roster entry in .gaia/audit-ci.yml covering backend/**, register any finding classes it needs, then run the roster check and repair everything it reports.
```

- **The name starts with `code-audit-`.** That registers it as part of the audit, so the [round limit](#the-branch-checkpoint) applies and an edit to its instructions sends every involved member back to review.
- **Finding classes** are kinds of problem the member reports. Registering new ones in `.gaia/finding-classes.json` lets [`/gaia-codify`](/maintenance/codify/#your-own-finding-classes) count them.

### The roster check

The roster check compares the roster with the files in your repository. The pre-commit hook runs it whenever a commit changes the roster, a member's agent file, or the audit's own files, and Claude repairs what it reports. It reports:

- A tracked file no member covers that is not on the `unowned:` list.
- A pattern, in the roster or `unowned:`, that matches no file.
- A member's agent file whose copy of its patterns no longer matches the roster. Claude regenerates it.
- A member whose name does not start with `code-audit-`.

The `unowned:` list in `.gaia/audit-ci.yml` holds paths you decided need no member, such as images. It only tells the roster check the gap is deliberate: those files still go to `code-audit-frontend`. When an update adds a member that covers an `unowned:` path, [`/update-gaia`](/maintenance/update-gaia/#what-it-does) removes the entry and says so.

GAIA's own folders (`.claude/`, `.gaia/`, `.githooks/`, `.github/audit/`) need no entry, even for files you add there.

### Library rules for code-audit-frontend

`code-audit-frontend` keeps rules for specific libraries in `apps/web/.claude/agents/code-audit-frontend/`, one Markdown file per library. GAIA ships files for `cn`, [Conform](https://conform.guide/), the form components, React buckets, react-i18next, and [shadcn/ui](https://ui.shadcn.com/). When you add, replace, or remove a library worth checking in review, ask Claude to add, replace, or delete its file:

```text
Add a code-audit-frontend library rule file for TanStack Query in apps/web/.claude/agents/code-audit-frontend/. Include the usage mistakes a reviewer should flag, with a bad and a good example for each, and send its rules to the react-patterns and typescript specialists.
```

Each file names the [rule specialists](/reference/agents/#audit-rule-specialist) that read it: `react-patterns`, `typescript`, or `translation`.

## Per-member clearance

Each member's approval (its clearance) covers what the branch changed in that member's files, plus the audit's own files: the roster, the members' agent files, the audit's scripts, `.github/audit/`, the root rules in `.claude/rules/`, and `.gaia/VERSION`. A change to the audit's own files sends back every member the pull request involves. On its own, with no member's files changed, it needs no review.

What you notice:

- **Members run in parallel.**
- **A commit outside a member's files never sends it back.** A docs or wiki change triggers no new review.
- **Merging `main` into your branch triggers no new review**, unless the merge commit has its own edit or a change lands within three lines of yours.

A member sent back looks only at what changed since its last verdict, plus its findings still open.

### Light review

A small change since a member's last full review can go to a cheaper Sonnet reviewer: up to 50 lines for `code-audit-frontend` and 30 for `code-audit-shell`, on by default. Some changes always get the full review: hooks, bats tests, and `.claude/settings.json` for shell; configs, `package.json`, the lockfile, tests, stories, workflows, and `CLAUDE.md` or `.claude/` files for frontend. When GAIA cannot confirm a change qualifies, the full member runs. Light review needs git 2.40 or later, which [`/setup-gaia`](/getting-started/setup-gaia/#1-prerequisites) and [`/update-gaia`](/maintenance/update-gaia/#what-it-does) check for. The settings are in [Agents](/reference/agents/#audit-light-reviewer).

The same reviewer can take a first review of a small, purely presentational frontend change (copy edits, swapped HTML tags, static class changes, translation text). It checks accessibility, translations, and theme color names, and asks one question: does anything need to block the merge? If yes, or unsure, the full member reviews it.

A member handed findings from the [code review](#the-code-review) always gets the full review.

## Severity

| Severity | Effect on approval |
|---|---|
| **Critical** | Must be fixed. |
| **Major** | Must be fixed, or acknowledged with a stated reason. |
| **Minor** | Never blocks approval. Fixed by default. |

Every finding, Minor included, gets an outcome. By default it is fixed. Otherwise it is waived, filed as an issue, or accepted as a known trade-off (a [residual](/maintenance/residue/#what-a-residual-is)), each with a reason. Only the loop's own stop or you can accept a residual. Findings about architecture come to you. A non-security finding on a line the branch wrote [is fixed or accepted](/reference/gates/#tech-debt-on-the-branchs-own-code), never filed.

### Out-of-scope findings

Findings outside the pull request's own change are filed as [`tech-debt` issues](/workflow/tech-debt/#how-an-issue-is-filed). A non-security one whose severity turns on a fact nobody has checked yet is filed as [`severity:investigate`](/workflow/tech-debt/#investigate-issues). A non-security finding in a file the pull request already changes can instead be recorded as waived, when this change did not cause it ([What gets recorded instead of filed](/workflow/tech-debt/#what-gets-recorded-instead-of-filed)).

### Security findings

Security findings are never filed publicly. See [Security findings](/workflow/tech-debt/#security-findings) for where they go instead.

## The audit loop

An `audit-loop-unit` sub-agent runs the rounds a few at a time, outside your main session. In each round the members review, a fixer repairs what they found, a script checks the repairs, and the Quality Gate runs before the fixes are committed. Your session holds only a short report per unit, so a long audit does not fill your context.

The loop needs **Claude Code 2.1.287 or later**. Run `claude update` if a unit stops and names the version.

### The code review

Before the first full member review, the loop runs Claude Code's `/code-review` once over the whole branch, at its `high` level, in a separate session that can only read. Each finding goes to the member that owns its file, or to `code-audit-frontend` for any other file. The member keeps a finding unless the member shows evidence that it is wrong, and a kept finding is fixed like one of the member's own. The review never clears a branch. Members alone do.

It runs once per branch, with one retry when a second try could pass, and has no setting to turn it off. The review is skipped when the light reviewer clears the branch on its first review, and on a GAIA update branch. On Claude Code older than 2.1.296, `## Audit rounds` shows the review as `not run` and the audit continues without it. A review that does not run never counts as clean and never blocks the merge. Only a review that changes your files, or runs past its time limit, stops the audit until you look.

### The branch checkpoint

Each round's fixes need review in the next, so the loop needs a stopping point. From round 3 through round 9 it stops on its own when a round finds only ordinary Minor findings in what changed: nothing Critical, Major, security-related, or repeated from an earlier round. Those are recorded as accepted residuals. In an interactive run Claude lists them and asks once, recommending neither: **Fix chosen ones** or **Merge**. An unattended run does not ask; you decide them later with [`/gaia-residue`](/maintenance/residue/).

Otherwise, GAIA checks in with you when:

- Your session's context reaches the [red band](/workflow/statusline/#the-context-bar)
- Rounds stop making progress
- The maximum number of rounds is reached

Claude shows where things stand (rounds, findings per round, what remains by severity, and the cost so far) and asks:

- **Continue audit in this session** or **in a new session**: one more batch of rounds. The new-session option prints a prompt to paste after `/clear`. On a [`/gaia-plan`](/workflow/plan/) build, that prompt returns to the plan, so its summary and merge question still come before the merge.
- **Accept the remainder**: offered only when the loop has a reason to stop, nothing Critical or security-related remains and every member's report came back complete. One last review round runs with no fixes, and what remains is recorded as accepted residuals.
- **Stop and file the remainder**: files the remaining findings as tech-debt issues and leaves the pull request open.

Only you can answer. If the question is not available, type one of these as the whole prompt:

```text
audit-grant <n>
```

```text
audit-accept
```

Claude never types either line for you. In an unattended run, Claude pushes the round's fixes, leaves the pull request open, and prints the `audit-grant` line for you to type later.

**Why:** a loop nobody watches keeps spending with no limit, and "is another round worth it?" should not be decided by the session least able to judge it. See the [gate reference](/reference/gates/#audit-checkpoint).

## Posting GAIA-Audit

Claude posts the `GAIA-Audit` success status last: once every involved member has approved the current change, every finding is fixed or recorded, the steps a [smaller gate](#what-it-checks) skipped have passed, and the last push has landed. If one of those steps fails, the loop reopens a round to fix it. Posting success also marks the draft pull request ready for review.

A member's refusal posts a `GAIA-Audit` failure at once, so GitHub's auto-merge cannot merge the pull request.

A pull request the audit does not need to review (every file outside its scope, or a manifest-only `chore(deps)` update from `/update-deps`) gets the check posted by the merge hook as `skipped`.

<Aside type="note">
A pull request merged from the GitHub UI without going through Claude (a raw [Dependabot](https://docs.github.com/en/code-security/dependabot) pull request, for example) never gets the check, so it waits on `GAIA-Audit` forever. Ask Claude to merge it once.
</Aside>

## What lands in the pull request

- **`## Audit rounds`**: total rounds, rounds per member, light reviews, rounds you granted, and the code review's outcome and cost.
- **`## Accepted residuals (recorded, not fixed)`**: accepted findings, which [`/gaia-residue`](/maintenance/residue/) reads later.
- **A findings comment**, posted on merge, with every round's findings. Security and Critical findings appear only as a count.

Each merge also prints the pull request's [cost](/models-and-context/cost/).

## Reading a refusal

If Claude tries to merge before the audit is done, the merge hook turns it back with one reason and one next step. Claude runs that step and tries again; nothing for you to do unless the table says so.

| Claude sees | What it means | Next step |
|---|---|---|
| A member has no clearance for the current change | That member has not reviewed the latest commit to its files, or refused it | Claude runs the audit loop. A refusal clears only when the finding is fixed or you acknowledge a Major finding with a reason. |
| The base tip is not a commit in this checkout | Your checkout has not fetched the base branch | Claude fetches it and retries. |
| GitHub cannot be reached | The audit cannot read the pull request's base branch | Claude shows the `gh` error. If it is a sign-in problem, run `gh auth login` yourself, since it opens a browser sign-in. |
| More than one merge base with the base tip | Git cannot tell what your branch changed | Claude merges the base branch into yours and retries. |
| A cross-repository (fork) pull request | A local audit would run the fork's scripts with your credentials | See [Fork pull requests](#fork-pull-requests). |

Every gate the audit can raise is in the [gate reference](/reference/gates/).

### Fork pull requests

GAIA never audits or merges a fork's pull request in your checkout, and a hook keeps Claude from checking out or fetching a fork's branch, since that would run the fork author's hooks and scripts with your credentials. To bring a fork's change in safely, copy its commits to a branch in your own repository without checking them out, and audit that branch. The steps are in the [gate reference](/reference/gates/#fork-pull-requests).

## Why the audit runs locally

Many teams run review, lint, and tests only on CI. GAIA runs them on your machine first and keeps CI as the backstop.

- **Sooner is cheaper.** A problem the gate or the audit finds is fixed while the change is fresh, in the same session. A problem CI finds arrives after you have moved on.
- **You can see and steer it.** You watch each round, answer its questions, and change course. Claude on CI is a black box.
- **It costs less.** Each member reviews only what changed since it last approved, inside the session you already have open.
- **Fixing stays simple.** The fixer repairs findings inside the loop, and the next round reviews the repairs. On CI, that takes extra machinery and another review.

CI still runs. The [Tests workflow](/workflow/git-conventions/#github-workflows-that-ship) runs lint and the test suites on every pull request, and once a repo admin has run `/setup-gaia`, its checks are required. The `GAIA-Audit` check confirms the local audit ran.

## Why the built-in review is not the gate

Claude Code's own review commands, such as `/code-review` and `/security-review`, are good reviewers. A merge gate needs four things they do not give you:

- **A reviewer you can hold steady.** Each member's instructions live in your repository, and changing them voids that member's clearances. A built-in review changes with Claude Code updates, so last month's clearance would still stand after it started checking different things.
- **Every owner signs off.** A change touching files owned by two members waits for both. A built-in review is one reviewer over the whole diff.
- **It holds the merge.** Claude cannot merge until every member has cleared. A built-in review only prints findings, and Anthropic's managed review on GitHub does not block a merge.
- **Every finding is dealt with.** Each one is fixed, waived with a reason, or filed as [tech debt](/workflow/tech-debt/), and recurring kinds feed [`/gaia-codify`](/maintenance/codify/). A built-in review's findings stay in the conversation.

So the audit uses `/code-review` only to [hand findings to the members](#the-code-review). When a Claude Code update changes what it checks, no member's clearance is voided, and it never clears or blocks a merge. You can still run it yourself as a second opinion.

## Whole-app security audits

The Code Audit Team reviews each pull request's diff, so it cannot see a security problem across files the diff never touches. For a periodic whole-app pass, you can run [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill), an open-source (MIT) skill. It is third-party: GAIA does not install, run, or maintain it.

Install it following its README, including the sandbox it needs. Then ask Claude to run it now and then, for example before a release, scoped and in its `quick` profile. Runs on the same repository build on each other. A scoped quick run on a GAIA project takes about 10 to 19 agents and 15 to 20 minutes.
