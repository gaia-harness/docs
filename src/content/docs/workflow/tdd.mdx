GAIA has Claude build features and fix bugs test-first, through the `tdd` skill, so you don't need to ask.

The skill runs a red-green-refactor loop: write one failing test (red), write just enough code to make it pass (green), tidy up (refactor), then move to the next behavior.

## Why test first

Writing the test before the code has three payoffs:

- **The test is proven to work.** A test written after the code passes on its first run, so you never learn whether it can fail. It may check nothing at all. Seeing it fail first, then pass once the code exists, shows it detects the behavior it describes.
- **The code ends up covered.** Code is only written to make a failing test pass, so every behavior has a test by the time it ships. Martin Fowler calls this [self-testing code](https://martinfowler.com/bliki/TestDrivenDevelopment.html).
- **The design starts from the caller.** Writing the test first makes Claude decide how the code will be used before how it works, which keeps the interface separate from the implementation.

Each loop is small, so a wrong turn costs one test, not a feature. Robert C. Martin describes the rhythm in [The Cycles of TDD](https://blog.cleancoder.com/uncle-bob/2014/12/17/TheCyclesOfTDD.html).

## The loop

1. **Plan.** Claude picks the layer the test belongs in (see [Where tests go](#where-tests-go)). It names each behavior a user can observe and the test that covers it. That is one test per behavior, not one per function. It asks you to approve that plan or revise it. It focuses on the critical paths and the complex logic, not every edge case.
2. **One tracer test.** One test that checks one thing from start to finish, to prove the test setup works before real coverage is added.
3. **One behavior at a time.** For each remaining behavior: one failing test, then only enough code to pass it. Claude writes tests only for the behaviors in the plan, plus a unit test where both [unit-test conditions](#where-tests-go) hold. Claude never writes all the tests first and all the code after. Tests written in bulk describe how Claude imagines the code will behave, not how it does.
4. **Refactor on green.** Once every test passes, Claude removes duplication and simplifies, running the tests after each step.

If a test still won't pass after a few focused attempts, Claude stops and tells you what is blocking it instead of reworking the code until something passes. The test, the interface, or an assumption may be wrong.

## What a good test looks like

A good test checks behavior through the code's public interface, the way a caller or a user would use it. It reads like a specification ("the user submits a valid form and sees a success message") and still passes after an internal refactor that keeps the behavior the same.

Tests mock only at the edges of the system: network requests, time, and randomness. Your own components, hooks, and services run for real.

### Which TDD style

TDD has two classic schools ([Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html#ClassicalAndMockistTesting)):

- **Detroit (classicist)**: real objects, checks the result.
- **London (mockist)**: outside-in, mocks every collaborator, checks how they are called.

GAIA takes from both:

- **Outside-in, like London.** A SPEC's [acceptance tests](#acceptance-tests-from-a-spec) are written first and fail until the feature works, and each tracer test starts from something a user can see.
- **Real collaborators and checked results, like Detroit.** Inside that outer loop, mocks stay at the edges of the system. A test asserts on what the user ends up seeing, never on whether a mock was called.

## Where tests go

GAIA follows the [testing trophy](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications), where most tests check pieces working together. In the React app, a route test is the default home for a behavior, story tests cover a component's behavior, and unit and browser tests stay few. A button's disabled state is a story, a click on it is a story test, and a route's redirect is a route test.

Claude writes a unit test only when both of these hold:

- **A route or story test cannot cover its cases cheaply.**
- **The logic is important or likely to fail.** Important means a wrong result would corrupt data, break sign-in or another access check, mishandle input from users or other systems, or miscalculate money, dates, or other values you rely on. Likely to fail means code that parses or cleans up input, applies rules with many edge cases, or runs work at the same time.

A formatting helper, a thin wrapper, or a small string, array, or object utility is covered by the tests that use it, or needs no test if nothing uses it. Each behavior a user can observe gets one test, and one test that runs over a table of cases (`test.each`) counts as one. Nothing the type checker or lint already proves gets a test. A tiny app gets few tests.

| Layer | Tool | What it checks |
|---|---|---|
| Component or page | A [Storybook](https://storybook.js.org/) story for each visual state, with a test attached for each behavior | What renders, user interactions, props, accessibility |
| Hook | `renderHook` from `vitest-browser-react` | Return values, state changes, callbacks |
| Utility or service | [Vitest](https://vitest.dev/) with [MSW](https://mswjs.io/) mocking the network | Parsed responses, request payloads, error cases |
| Route | A route module's `loader` or `action` called with a `Request` in Vitest, no browser and no server, in `app/route-tests/<feature>/tests/` | Status, redirect, returned data, validation errors, authorization outcome, side effects, including page text that only shows what the loader returns, and a refusal or error even when an error page shows it |
| Real server | [Playwright](https://playwright.dev/) sending requests to the dev server, with no page. Rendered HTML is read with the `parseHtml` helper in `apps/web/.playwright/html.ts` | What only the live server shows, such as middleware, the HTTP status a guarded route serves for a refusal, a forged request whose guard a direct loader or action call skips, the form the server serves, a flow through several plain HTML forms, or server-rendered HTML that is a requirement of its own. `serializeForm`, in the same file, builds the form body from the page the server returned |
| Browser | Playwright driving a real page against the dev server | Client JavaScript (an update without a reload), layout or position on screen, focus or the keyboard, an accessibility scan of the rendered page, or browser navigation such as the back button. Nothing else needs a browser. One browser test per user flow |

**What a route test cannot prove.** It calls the loader or action directly, so it skips middleware: a guard there needs a live-server check. On a single-fetch request, a parent route's loader guards neither a child's action nor its loader, so each write action guards itself and its own test proves it, and a parent-loader guard on a read needs a live-server check. And it cannot prove an authorization outcome an upstream API owns, because the MSW handler answers however the test wrote it.

**Playwright workers each get their own database.** Once your project adds a real database, each parallel Playwright worker gets its own server and database, and test setup writes to that worker's database through builders. Keep the builders in a file you own, such as `apps/web/.playwright/project-fixtures.ts`, because GAIA replaces its `fixtures.ts` on update.

**Stories are the component tests.** A story shows one visual state of a component, and each behavior is a named test attached to that story with `.test()`. The test clicks and types like a user and checks the result, in a real Chromium browser. A story can also have a play function, a script that clicks or types to bring the component into the state the story shows, but it checks nothing itself. Each test is reported by its own name, so a failure tells you which behavior broke. Claude does not write a separate test file that renders the component again.

This is Storybook's newer story format, CSF Next. A story file still in the old format is sent back with the command that converts it. Every story is also checked for accessibility, and a story that opts out of that check fails the tests unless the opt-out is recorded with a reason in `apps/web/test/story-a11y-opt-out.test.tsx`. Each story then runs again in the dark theme, where it fails on an accessibility problem, a console error, or rendering nothing.

Stories and hook tests need Chromium. [`/gaia-init`](/getting-started/gaia-init/) and [`/setup-gaia`](/getting-started/setup-gaia/) install it. On another machine, ask Claude to install the test browsers. The install adds system libraries and can ask for your password, so Claude hands you the command to type:

```
! pnpm install:browsers
```

## Proving a test can fail

A test that passed from the start may not test anything. GAIA checks this in two ways. A test of code with predictable output must be seen failing first, and every changed test also gets a worthiness review.

### Code with predictable output: seen failing first

For code that gives the same result every run (utilities, service parsers, most hooks, and route tests), a test must be seen failing before it passes. When Claude runs the tests, GAIA records every test that fails. If Claude tries to commit a new test with no recorded failure for its current content, a hook sends the commit back. Editing or renaming an existing test never needs a new failure.

Claude first writes a placeholder for the new code that returns the wrong value. The placeholder already has the code's final name, parameter types, and return type, and is async if the real code will be. Claude writes the test against that, so the test fails because the real code is missing. Then it writes the code. It never breaks working code to force a failure.

When the gate stops a commit, Claude runs the test file on its own, as a separate command, while it fails, so the failure is recorded, then makes it pass. If the code already exists, the test can no longer fail honestly, so Claude names the test to you instead of breaking the code. See [the RED gate](/reference/gates/#test-seen-failing-first-red-gate) for the exemptions.

### The worthiness review

Every changed test gets this review once the tests pass. A separate reviewer with no shared context reads each one, plus the test files next to it. The session that wrote the tests never judges them, since it would share their blind spots.

Some tests cannot be reliably watched failing first, such as stories, component interaction tests, async tests, and Playwright tests. For them, this review is also the proof that a test can fail. Each test is judged on two questions:

- **Can it fail for a real reason?** It must check what a user can see and do (roles, accessible names, visible text), not internal details. A test of predictable code skips this question, because seeing it fail first already answered it. Route tests are the exception and get both questions.
- **Is it worth keeping?** It should test your code, not a library's. A parent component's test should cover how its children work together, not repeat what each child's tests already check. A test of formatted output checks your logic (the conversion, the locale chosen), not the exact characters `Intl` produces. A unit test fails this question when a route or story test already checks the same thing, when it proves what the type checker or lint already proves, or when its logic is neither important nor likely to fail. Several tests of one function that could share one table of cases should be one test.

For an interactive component, the reviewer also expects its story tests to drive it from the keyboard and check where focus lands. An accessibility scan of a rendered component tests neither.

Each test gets one verdict: keep, fix, or delete. The reviewer edits no test or source file itself.

### The worthiness step

A plan run, a plain request, and `/gaia-debt` each finish this review once the draft pull request is open and before the first audit round. If the branch changed no test in the React app, or every changed test already has a verdict, the step ends with no commit.

- **Keep**: nothing more happens. A test that already has a keep for its current content is not reviewed again.
- **Fix**: a fresh sub-agent fixes the test, Claude commits, and the reviewer judges the changed test once more. If it still gets a fix verdict, or the fixer cannot fix it, it becomes an [accepted residual](/maintenance/residue/#what-a-residual-is). If it now gets a delete verdict, the delete steps below apply. A fix for a test this branch did not change goes to [tech debt](/workflow/tech-debt/) instead.
- **Delete**: Claude shows you the evidence (the redundant assertion and the test that already covers it) and asks you to confirm the delete or keep the test. An approved delete goes to the same fixer. A test rendered from a SPEC's UAT never gets a delete verdict: if it no longer matches, the SPEC is [reopened](/workflow/spec/#reopening-a-saved-spec) instead. A refused delete keeps the test with no residual. In an unattended run, the test stays and a residual is recorded.

If an audit fixer changes a test after it was judged and it now gets a fix verdict, Claude asks you. Fixing it means another review and one more CI run. The alternative is an accepted residual.

### The overlap pass

A check one test already proves does not need a second test. After the worthiness step, a plan run looks for tests the branch changed that repeat what another test already checks, across stories and unit tests, route tests, real-server tests, and browser tests. It also finds browser tests that check only a status, a redirect, or server-rendered text, which a real-server test can check without a browser. It runs once per plan run, if the branch changed any test.

An `overlap-evaluator` sub-agent proposes, for each duplicate, to drop it, merge it into the other test, move it to another layer, or keep both. It can also propose deleting several tests when one existing route, story, or real-server test already checks everything they check. Nothing new is written. When combining them would need a new test, the proposal is only listed in the summary and the pull request description, never applied. A proposal to drop or move a route, real-server, or browser test and leave only a unit test covering it must say why both [unit-test conditions](#where-tests-go) hold.

A browser test that needs no browser is proposed as a real-server test even when no other test covers it yet, but a flow's only browser test always stays. You see every proposal in one list, with the test it would rely on, and answer once: accept all as recommended, or revise. Proposals the sub-agent is unsure of are marked `Uncertain:` and come last, and any changed test with no proposal is named with the reason. Proposals on a test rendered from a SPEC, or on code the branch did not write, are listed for information and never applied. In an unattended run nothing changes: the proposals are listed in the plan's progress file and the final summary.

## What you see at the end

When the work is done, Claude's summary shows:

- **Each source file it touched, and whether it counts as predictable.** A predictable file's new tests must be seen failing first. For any other file, the worthiness review also checks that its tests can fail. Every file is listed, so a wrong call is visible.
- **Honesty fixes**, already made. A test that could not fail for a real reason is rewritten in place, and you review it like any other edit.
- **Proposed deletes**, each with its evidence. Claude asks you about each one, as in [the worthiness step](#the-worthiness-step).

The list shows the most severe findings first, with a count when there are more. Before merging, a hook checks that every changed test has a review on record for its current content. See [the worthiness verdict gate](/reference/gates/#worthiness-verdict).

## Acceptance tests from a SPEC

When you build from a [SPEC](/workflow/spec/), its acceptance tests become Vitest route tests or Playwright tests, by the layer that can show each outcome, and are expected to fail before any code is written. Each one stops failing when the phase that builds its behavior is done. See [UAT specs](/workflow/plan/#uat-specs).

## Testing another stack

The loop works for any language. Before the first test, the `tdd` skill reads the reference for the stack it is testing. Two ship:

- **React**: the `tdd-react` skill, for the app in `apps/web/`.
- **Shell**: for the shell scripts your own skills and hooks run, tested with [bats](https://github.com/bats-core/bats-core). Tests go in `tests/shell/`, one file per script, and `pnpm test:shell` runs them. GAIA installs bats as a dev dependency, so there is nothing else to install. The runner refuses to start under a bash older than 4, because bash 3.2 (the default on macOS) lets some failing tests pass. On a Mac, ask Claude to put a newer bash first on your `PATH`. The `bats-assertions` [rule](/reference/rules/#path-scoped-root) loads whenever Claude edits a `.bats` file, so it writes checks that can actually fail. The Tests workflow runs the suites on pull requests that change shell (see [GitHub workflows that ship](/workflow/git-conventions/#github-workflows-that-ship)).

When you add a backend or another package, give Claude the equivalent reference for it:

```text
Add a TDD stack reference for <stack> in <folder>, following the pattern of the tdd-react skill: test layers, where each kind of test lives, what to mock, and good and bad examples. Then point the tdd skill's stack list at it.
```
