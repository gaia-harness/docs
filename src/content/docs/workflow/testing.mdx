GAIA's rule is to test what matters, after the code exists. The rule is part of the coding guidelines every session loads, so you don't need to ask for tests. Every test the work changes then gets an independent [worthiness review](#the-worthiness-review), and a merge gate checks that the review ran.

## What gets a test

Once the code exists, Claude writes these tests.

- **One test per critical user flow**, starting where a user starts it, covering its happy path and each error path the code has. A SPEC names these flows (see [Flow tests from a SPEC](#flow-tests-from-a-spec)).
- **A route test** where a route's behavior is worth locking in.
- **A unit test** for tricky logic.
- **A test that reproduces the bug**, for each bug fix.

Writing the test first is optional. See [Test-driven development with `/tdd`](#test-driven-development-with-tdd).

GAIA follows the [testing trophy](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications). Most tests check pieces working together, and there are not too many of them. A behavior a user can observe gets at most one test, and one test that runs over a table of cases (`test.each`) counts as one. That is a limit, not a target. A behavior a flow test already covers gets no test of its own, but the tests listed above are still written. Nothing the type checker or lint already proves gets a test. A tiny app gets few tests.

Claude writes a unit test only when both of these hold.

- **A route or story test cannot cover its cases cheaply.**
- **The logic is important or likely to fail.** Important means a wrong result would corrupt data, break sign-in or another access check, mishandle input from users or other systems, or miscalculate money, dates, or other values you rely on. Likely to fail means code that parses or cleans up input, applies rules with many edge cases, or runs work at the same time.

A formatting helper, a thin wrapper, or a small string, array, or object utility is covered by the tests that use it, or needs no test if nothing uses it.

## What a good test looks like

A good test checks behavior through the code's public interface, the way a caller or a user would use it. It reads like a specification ("the user submits a valid form and sees a success message") and still passes after an internal refactor that keeps the behavior the same.

Tests mock only at the edges of the system, such as network requests, time, and randomness. Your own components, hooks, and services run for real.

## Where tests go

In the React app, a route test is the default home for a behavior, story tests cover a component's behavior, and unit and browser tests stay few. A button's disabled state is a story, a click on it is a story test, and a route's redirect is a route test.

| Layer | Tool | What it checks |
|---|---|---|
| Component or page | A [Storybook](https://storybook.js.org/) story for each visual state, with a test attached for each behavior | What renders, user interactions, props, accessibility |
| Hook | `renderHook` from `vitest-browser-react` | Return values, state changes, callbacks |
| Utility or service | [Vitest](https://vitest.dev/) with [MSW](https://mswjs.io/) mocking the network | Parsed responses, request payloads, error cases |
| Route | A route module's `loader` or `action` called with a `Request` in Vitest, no browser and no server, in `app/route-tests/<feature>/tests/` | Status, redirect, returned data, validation errors, authorization outcome, side effects, including page text that only shows what the loader returns, and a refusal or error even when an error page shows it |
| Real server | [Playwright](https://playwright.dev/) sending requests to the dev server, with no page, in `apps/web/.playwright/e2e/`. Rendered HTML is read with the `parseHtml` helper in `apps/web/.playwright/html.ts` | What only the live server shows, such as middleware, the HTTP status a guarded route serves for a refusal, a forged request whose guard a direct loader or action call skips, the form the server serves, a flow through several plain HTML forms, or server-rendered HTML that is a requirement of its own. `serializeForm`, in the same file, builds the form body from the page the server returned |
| Browser | Playwright driving a real page against the dev server, in `apps/web/.playwright/e2e/` | Client JavaScript (an update without a reload), layout or position on screen, focus or the keyboard, an accessibility scan of the rendered page, or browser navigation such as the back button. Nothing else needs a browser, and a [critical flow's test](#flow-tests-from-a-spec) is the one exception. One browser test per user flow |

**What a route test cannot prove.** It calls the loader or action directly, so it skips middleware, and a guard there needs a live-server check. On a single-fetch request, a parent route's loader guards neither a child's action nor its loader, so each write action guards itself and its own test proves it, and a parent-loader guard on a read needs a live-server check. And it cannot prove an authorization outcome an upstream API owns, because the MSW handler answers however the test wrote it.

**Playwright workers each get their own mock data.** A Playwright test can run against a dev server of its own for each parallel worker. Test setup adds the records a test needs to that server's mock API through builders, so workers never share data. Keep the builders in a file you own, such as `apps/web/.playwright/project-fixtures.ts`, because GAIA replaces its `fixtures.ts` on update.

**A real backend is yours to test.** GAIA's tests run against the mock API, never your backend. A SPEC lists anything only a real backend can show, such as data surviving a restart, as yours to test end to end. GAIA writes no test for it. To run the same Playwright tests against your backend, swap in builders that add records to it and point the tests at a server running without the mock API.

**Stories are the component tests.** A story shows one visual state of a component, and each behavior is a named test attached to that story with `.test()`. The test clicks and types like a user and checks the result, in a real Chromium browser. A story can also have a play function, a script that clicks or types to bring the component into the state the story shows, but it checks nothing itself. Each test is reported by its own name, so a failure tells you which behavior broke. Claude does not write a separate test file that renders the component again.

This is Storybook's newer story format, CSF Next. A story file still in the old format is sent back with the command that converts it. Every story is also checked for accessibility, and a story that opts out of that check fails the tests unless the opt-out is recorded with a reason in `apps/web/test/story-a11y-opt-out.test.tsx`. Each story then runs again in the dark theme, where it fails on an accessibility problem, a console error, or rendering nothing.

Stories and hook tests need Chromium. [`/gaia-init`](/getting-started/gaia-init/) and [`/setup-gaia`](/getting-started/setup-gaia/) install it. On another machine, ask Claude to install the test browsers. The install adds system libraries and can ask for your password, so Claude hands you the command to type:

```
! pnpm install:browsers
```

## Flow tests from a SPEC

A [SPEC](/workflow/spec/) names the feature's [critical flows](/workflow/spec/#critical-flows). When [`/gaia-plan`](/workflow/plan/) builds from it, the build comes first, then a final phase writes one test per flow. For a flow in the web app, the test is a Playwright test in `apps/web/.playwright/flows/`, named after the flow, and it may drive a real browser even when a cheaper layer could check the same thing. A command-line flow's test goes where the SPEC says. Before the audit, GAIA checks that every flow has its test and that the branch changed it. See [Flow tests](/workflow/plan/#flow-tests).

## How GAIA judges tests

A test that passes may still check nothing. GAIA has a separate reviewer judge every changed test, then fixes the ones that fall short and asks you before deleting any.

### The worthiness review

Every test the work changes in the React app gets this review once the tests pass, and so does every flow test. A separate reviewer with no shared context reads each one, plus the test files next to it. The session that wrote the tests never judges them, since it would share their blind spots.

Nothing checks mechanically that a test can fail, so this review is what judges it. Each test is judged on two questions:

- **Can it fail for a real reason?** It must check what a user can see and do (roles, accessible names, visible text), not internal details, and must not assert something that is always true.
- **Is it worth keeping?** It should test your code, not a library's. A parent component's test should cover how its children work together, not repeat what each child's tests already check. A test of formatted output checks your logic (the conversion, the locale chosen), not the exact characters `Intl` produces. A unit test fails this question when a route or story test already checks the same thing, when it proves what the type checker or lint already proves, or when its logic is neither important nor likely to fail. Several tests of one function that could share one table of cases should be one test.

For an interactive component, the reviewer also expects its story tests to drive it from the keyboard and check where focus lands. An accessibility scan of a rendered component tests neither.

A flow test is also judged against its flow in the SPEC. The reviewer names each error path the code has that no test in the file exercises, an outcome the test never checks (a heading after submit, but never that the save took effect), and, for a web app flow, any app folder the branch changed for the flow that the test's `@covers` line leaves out. That line is a comment at the top of the test that lists the app folders the flow runs through. Any of these makes the verdict a fix.

Each test gets a keep, fix, or delete verdict. The reviewer edits no test or source file itself.

### The worthiness step

A plan run, a plain request, and `/gaia-debt` each finish this review once the draft pull request is open and before the first audit round. If no changed test needs a verdict, the step ends with no commit.

- **Keep**: nothing more happens. A test that already has a keep for its current content is not reviewed again.
- **Fix**: a fresh sub-agent fixes the test, GAIA commits the fix, and the reviewer judges the changed test once more. If it still gets a fix verdict, or the fixer cannot fix it, it becomes an [accepted residual](/maintenance/residue/#what-a-residual-is). If it now gets a delete verdict, the delete steps below apply. A fix for a test this branch did not change goes to [tech debt](/workflow/tech-debt/) instead.
- **Delete**: Claude shows you the evidence (the redundant assertion and the test that already covers it) and asks you to confirm the delete or keep the test. An approved delete goes to the same fixer. A refused delete keeps the test with no residual. In an unattended run, the test stays and a residual is recorded.

If an audit fixer changes a test after it was judged and it now gets a fix verdict, Claude asks you. Fixing it means another review and one more CI run. The alternative is an accepted residual.

### The overlap pass

A check one test already proves does not need a second test. After the worthiness step, a plan run looks for tests the branch changed that repeat what another test already checks, across stories and unit tests, route tests, real-server tests, and browser tests. It also finds browser tests that check only a status, a redirect, or server-rendered text, which a real-server test can check without a browser. It runs once per plan run, if the branch changed any test.

An `overlap-evaluator` sub-agent proposes, for each duplicate, to drop it, merge it into the other test, move it to another layer, or keep both. It can also propose deleting several tests when one existing route, story, or real-server test already checks everything they check. When combining them would need a new test, the proposal is only listed in the summary and the pull request description, never applied. A proposal to drop or move a route, real-server, or browser test and leave only a unit test covering it must say why both [unit-test conditions](#what-gets-a-test) hold.

A browser test that needs no browser is proposed as a real-server test even when no other test covers it yet, but a flow's only browser test always stays. You see every proposal in one list, with the test it would rely on, and answer once, to accept all as recommended or revise. Proposals the sub-agent is unsure of are marked `Uncertain:` and come last, and any changed test with no proposal is named with the reason. Proposals on code the branch did not write are listed for information and never applied. In an unattended run nothing changes, and the proposals are listed in the plan's progress file and the final summary.

### What you see at the end

The summary at the end of the work lists what the worthiness step decided, such as accepted residuals, deletes you refused, and fixes filed as tech debt. A plan run's summary adds the overlap pass result.

Before merging, a hook checks that every changed test has a review on record for its current content. See [the worthiness verdict gate](/reference/gates/#worthiness-verdict).

## Test-driven development with `/tdd`

Test-driven development (TDD) writes each test before the code that makes it pass. It is opt-in in GAIA, a tool for logic where writing the test first helps, such as a parser or a rule with many edge cases. Type `/tdd` with what to build, or ask Claude to build it test-first:

```
/tdd a parser for the import file's date column
```

Seeing a test fail before the code exists shows it can catch the bug it describes. Writing it first also makes Claude decide how the code will be used before how it works. Martin Fowler covers the practice in [Test Driven Development](https://martinfowler.com/bliki/TestDrivenDevelopment.html).

### The loop

1. **Plan.** Claude picks the layer the test belongs in (see [Where tests go](#where-tests-go)). It names each behavior a user can observe and the one test that covers it, not one test per function. One test can cover several behaviors, and a behavior that already has a test extends that test instead of getting a second. It asks you to approve that plan or revise it. It focuses on the critical paths and the complex logic, not every edge case.
2. **One tracer test.** One test that checks one thing from start to finish, to prove the test setup works before real coverage is added.
3. **One behavior at a time.** For each remaining behavior, one failing test, then only enough code to pass it. Claude never writes all the tests first and all the code after, because tests written in bulk describe how Claude imagines the code will behave, not how it does.
4. **Refactor on green.** Once every test passes, Claude removes duplication from the code this cycle wrote and moves complexity behind simpler interfaces, running the tests after each step.

Before writing the code, Claude runs each new test and checks that it fails for the right reason. It first writes a placeholder with the code's final name and types that returns the wrong value, then writes the test against it, so the test fails because the real code is missing. It never breaks working code to force a failure. When the code already exists, Claude writes the test against it as it is, and the worthiness review judges it like any other.

If a test still won't pass after a few focused attempts, Claude stops and tells you what is blocking it instead of reworking the code until something passes. The test, the interface, or an assumption may be wrong.

At the end, Claude's summary lists each source file it touched, then the worthiness review's verdicts, most severe first, with a count when there are more. A test that could not fail for a real reason is already rewritten in place, and you review it like any other edit. Claude asks you about each proposed delete, showing its evidence.

## Testing another stack

GAIA ships testing references for two stacks.

- **React**: the `tdd-react` skill, for the app in `apps/web/`.
- **Shell**: for the shell scripts your own skills and hooks run, tested with [bats](https://github.com/bats-core/bats-core). Tests go in `tests/shell/`, one file per script, and `pnpm test:shell` runs them. GAIA installs bats as a dev dependency, so there is nothing else to install. The runner refuses to start under a bash older than 4, because bash 3.2 (the default on macOS) lets some failing tests pass. On a Mac, ask Claude to put a newer bash first on your `PATH`. The `bats-assertions` [rule](/reference/rules/#path-scoped-root) loads whenever Claude edits a `.bats` file, so it writes checks that can actually fail. The Tests workflow runs the suites on pull requests that change shell (see [GitHub workflows that ship](/workflow/git-conventions/#github-workflows-that-ship)).

When you add a backend or another package, give Claude the equivalent reference for it:

```text
Add a testing reference for <stack> in <folder>, following the pattern of the tdd-react skill: test layers, where each kind of test lives, what to mock, and good and bad examples. Then point the tdd skill's stack list at it.
```
