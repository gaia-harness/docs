GAIA's rule is to test what matters, after the code exists. GAIA's testing rules decide which test to write and at which layer, and every session and sub-agent follows them, so you don't need to ask for tests. A plan decides its tests before any code exists, in a [test-design table](#the-test-design-table). Other work gets an independent [worthiness review](#the-worthiness-review). A [merge gate](/reference/gates/#worthiness-verdict) checks that every changed test was judged.

## What gets a test

Claude tests only what was asked for. That means a SPEC's flows, success criteria, and answered questions, a plan's description, or your issue or request. A corner case or error path none of them names gets no test. Once the code exists, Claude writes these tests.

- **One test per critical user flow**, starting where a user starts it, covering its journey through the happy path and the happy path's effects that take several requests or sessions to set up, such as signing out ending a session. A SPEC names these flows (see [Flow tests from a SPEC](#flow-tests-from-a-spec)).
- **A test for each guard** the code adds, meaning code that refuses, such as an access check or a validation. The test makes the guard refuse, at the lowest layer that shows it, usually a route test. A test that only watches a guard pass cannot tell a working guard from a broken one.
- **A unit test** for tricky logic.
- **A test that reproduces the bug**, for each bug fix.

Writing the test first is optional. See [Test-driven development with `/tdd`](#test-driven-development-with-tdd).

GAIA follows the [testing trophy](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications). Most tests check pieces working together, and there are not too many of them. A behavior a user can observe gets at most one test, and one test that runs over a table of cases (`test.each`) counts as one. That is a limit, not a target. A happy path gets no test of its own when a flow test walks it and checks its effect, but an effect the flow test cannot see keeps its own route test, and a flow test repeats no refusal another test already checks. Nothing the type checker or lint already proves gets a test. A tiny app gets few tests.

Claude writes a unit test only when both of these hold.

- **A route or story test cannot cover its cases cheaply.**
- **The logic is important or likely to fail.** Important means a wrong result would corrupt data, break sign-in or another access check, mishandle input from users or other systems, or miscalculate money, dates, or other values you rely on. Likely to fail means code that parses or cleans up input, applies rules with many edge cases, or runs work at the same time.

A formatting helper, a thin wrapper, or a small string, array, or object utility is covered by the tests that use it, or needs no test if nothing uses it.

## What a good test looks like

A good test checks behavior through the code's public interface, the way a caller or a user would use it. It reads like a specification ("the user submits a valid form and sees a success message") and still passes after an internal refactor that keeps the behavior the same.

Tests mock only at the edges of the system, such as network requests, time, and randomness. Your own components, hooks, and services run for real.

## Where tests go

In the React app, a route test is the default home for a behavior, story tests cover a component's behavior, and unit and browser tests stay few. A button's disabled state is a story, a click on it is a story test, and a route's redirect is a route test.

| Layer | Tool | What it checks |
|---|---|---|
| Component or page | A [Storybook](https://storybook.js.org/) story for each visual state, with a test attached for each behavior | What renders, user interactions, props, accessibility |
| Hook | `renderHook` from `vitest-browser-react` | Return values, state changes, callbacks |
| Utility or service | [Vitest](https://vitest.dev/) with [MSW](https://mswjs.io/) mocking the network | Parsed responses, request payloads, error cases |
| Route | A route module's `loader` or `action` called with a `Request` in Vitest, no browser and no server, in `app/route-tests/<feature>/tests/` | Status, redirect, returned data, validation errors, authorization outcome, side effects, including page text that only shows what the loader returns, and a refusal or error even when an error page shows it |
| Real server | [Playwright](https://playwright.dev/) sending requests to the dev server, with no page, in `apps/web/.playwright/e2e/`. Rendered HTML is read with the `parseHtml` helper in `apps/web/.playwright/html.ts` | What only the live server shows, such as middleware, the HTTP status a guarded route serves for a refusal, a forged request whose guard a direct loader or action call skips, the form the server serves, plain HTML form posts that belong to no [critical flow's test](#flow-tests-from-a-spec), or server-rendered HTML that is a requirement of its own. `serializeForm`, in the same file, builds the form body from the page the server returned |
| Browser | Playwright driving a real page against the dev server, in `apps/web/.playwright/e2e/` | Client JavaScript (an update without a reload), layout or position on screen, focus or the keyboard, an accessibility scan of the rendered page, or browser navigation such as the back button. Nothing else needs a browser, and a [critical flow's test](#flow-tests-from-a-spec) is the one exception. One browser test per user flow |

**What a route test cannot prove.** A route test that calls the loader or action directly skips middleware. A middleware guard is tested by a route test that runs the real middleware chain, or else by a live-server check, never by a unit test that calls the middleware itself, which cannot show the guard is wired in. On a single-fetch request, a parent route's loader guards neither a child's action nor its loader, so each write action guards itself and its own test proves it, and a parent-loader guard on a read needs a live-server check. And it cannot prove an authorization outcome an upstream API owns, because the MSW handler answers however the test wrote it. What your app does with an upstream refusal, such as creating no session and showing the error, is still tested, as an access [security row](#security-tests).

**Playwright workers each get their own mock data.** A Playwright test can run against a dev server of its own for each parallel worker. Test setup adds the records a test needs to that server's mock API through builders, so workers never share data. Keep the builders in a file you own, such as `apps/web/.playwright/project-fixtures.ts`, because GAIA replaces its `fixtures.ts` on update.

**A real backend is yours to test.** GAIA's tests run against the mock API, never your backend. A SPEC lists anything only a real backend can show, such as data surviving a restart, as yours to test end to end. GAIA writes no test for it. To run the same Playwright tests against your backend, swap in builders that add records to it and point the tests at a server running without the mock API.

**Stories are the component tests.** A story shows one visual state of a component, and each behavior is a named test attached to that story with `.test()`. The test clicks and types like a user and checks the result, in a real Chromium browser. A story can also have a play function, a script that clicks or types to bring the component into the state the story shows, but it checks nothing itself. Each test is reported by its own name, so a failure tells you which behavior broke. Claude does not write a separate test file that renders the component again.

This is Storybook's newer story format, CSF Next. A story file still in the old format is sent back with the command that converts it. Every story is also checked for accessibility, and a story that opts out of that check fails the tests unless the opt-out is recorded with a reason in `apps/web/test/story-a11y-opt-out.test.tsx`. Each story then runs again in the dark theme, where it fails on an accessibility problem, a console error, or rendering nothing.

Stories and hook tests need Chromium. [`/gaia-init`](/getting-started/gaia-init/) and [`/setup-gaia`](/getting-started/setup-gaia/) install it. On another machine, ask Claude to install the test browsers. The install adds system libraries and can ask for your password, so Claude hands you the command to type:

```
! pnpm install:browsers
```

## Flow tests from a SPEC

A [SPEC](/workflow/spec/) names the feature's [critical flows](/workflow/spec/#critical-flows). When [`/gaia-plan`](/workflow/plan/) builds from it, the build comes first, then a final phase writes one test per flow, except a flow whose every step the build's tests already check (see [Flow tests](/workflow/plan/#flow-tests)). For a flow in the web app, the test is a Playwright test in `apps/web/.playwright/flows/`, named after the flow, and it may drive a real browser even when a cheaper layer could check the same thing. A command-line flow's test goes where the SPEC says. Before the audit, GAIA checks that every flow has its test and that the branch changed it. See [Flow tests](/workflow/plan/#flow-tests).

## How GAIA judges tests

A test that passes may still check nothing. A plan checks its tests against its [test-design table](#the-test-design-table) with the [drift check](#the-drift-check). Other work, such as a plain request, `/gaia-debt`, or a plan made by an older GAIA version, gets the [worthiness review](#the-worthiness-review) on every test it changes.

### The test-design table

[`/gaia-plan`](/workflow/plan/) decides every test before any code is written. The plan's table gives each test a row. A row names the requirement the test proves, the case, its file and exact title, its layer, the task that writes it, and one action.

- **New**: write a test no existing test holds.
- **Reuse**: an existing test already checks the case. It stays unchanged.
- **Extend**: add the case to an existing test's table of cases.
- **Change**: the plan changes the behavior an existing test checks, so the test changes too.
- **Retire**: the new work replaces an existing test, so it is deleted.

The planner first reads the existing tests for the code the plan touches, so a case they already check is reused or extended, not written again. Every requirement maps to at least one row and every row to a requirement, so a missing or duplicate test shows up in the table, before the build. A SPEC scope boundary that steers the build instead of saying what the app does, such as "ask before adding a dependency", gets no row. The plan records it with what it directs instead. The [plan audit](/workflow/plan/#the-plan-audit) reviews the table, and approving the plan approves it, retired tests included. The plan's `README.md` shows it under `## Test design`.

Each task's sub-agent writes the tests its rows give it, under the planned titles, and never edits the table.

### Security tests

A security row is a row whose test proves one of three things:

- **Access**: who may act or see something. This includes signing in and its refusals, such as a wrong password, as well as roles, ownership, and account states such as a suspended account, and what a page offers only to those who may use it, such as an action, form, link, or menu item.
- **Forgery**: a forged or edited value is refused. So is an untrusted destination the server would send the user or a request to, such as an off-site redirect target or an unregistered callback URL, or the server swaps in an allowed one.
- **Secrets**: a secret never appears where it must not. Any value a requirement keeps on the server counts, even one that looks harmless, such as an API base URL.

The table marks each security row with a flag. A separate sub-agent, `security-test-writer`, writes these tests at the end of the phase that builds the code. It writes each one from the row and the plan's shared contracts, and reads the code only to find where to call it, so its test cannot repeat the code's mistake.

The flag is decided for each case a test checks, not for the test as a whole. When one test checks cases of different kinds, such as a signed-out redirect beside a signed-in page, each kind gets its own row, so the refusal is flagged and goes to the security writer. A test that runs one case per table entry keeps the cases together with a row for each. Any other test is split, one test per kind. Splitting a test never removes a flag.

A security row can sit on a story, such as a check that a control is hidden from a user who may not use it. It adds to the route or real-server test the guard needs, never replaces it. A forgery check goes on a story only as a change to an existing story test, beside its server-side test.

A row that retires or changes an existing test is a security row too when that test is one, or when a security requirement forbids what the old test checked, such as a value the plan now keeps on the server that the old test showed reaching the browser. It takes that requirement's kind. So does a row that retires a test a security row for the same requirement now covers; it takes that row's kind. Retiring either counts as retiring a security test. Any other row that cites a security requirement only because that work deletes or rewrites the tested code keeps the old test's own kind.

When a security test fails, a fresh sub-agent fixes the code, never the test. If it fails again, the plan stops and asks you what to do. Only you can rule a security row wrong or retire a security test. Approving a plan approves retiring the security test of code the plan deletes, and no other. Any other security test retire is held for you to decide before merge, and so is that one if the code is still there at merge. A run no one approved, such as [auto mode](/workflow/plan/#auto-mode) or a headless run, holds every security test retire.

Before merge, a gate stops the merge while an approved security row has no test from the writer. See [the security test gate](/reference/gates/#security-test-missing).

### The drift check

Drift is any gap between the branch's tests and the approved table. After the last phase, a script compares the two and GAIA routes each gap:

- **A test that matches its row** gets an honesty read. A separate checker confirms the test really checks its row's case. A hollow test is fixed and read again.
- **A planned test that is missing** is written from its row. A security row's test goes back to the security writer.
- **A planned test that was only renamed** keeps its row, which GAIA retitles.
- **A test no row names, or one moved to another file,** gets the [worthiness review](#the-worthiness-review). A test it keeps gains a row with a reason. GAIA asks you before any delete.
- **A test the branch deleted that no row retires** comes to you. GAIA recommends keeping it, which restores the test.

A test is hollow when its check can never fail. A guard test that never makes the guard refuse counts. So does a test that checks the app's own copy of a string instead of the wording you stated, one that tests a mock instead of the app, and one whose check sits in a story's play function. A skipped, to-do, or empty test counts as no test.

An unchanged test no row names is not drift. The [Code Audit Team](/workflow/code-audit-team/) runs the same check after each round that commits a fix, on the tests that round changed, and once more after the audit clears. Those runs ask you nothing. A delete becomes a residual, and a test deleted without a retire row is restored.

### The worthiness review

Work without a test-design table gets this review on every test it changes in the React app, flow tests included, once the tests pass. A plan uses it only for the tests its table does not name. A separate reviewer with no shared context reads each test, plus the test files next to it and, for a test of a shared helper, the tests of the helper's other callers. The session that wrote the tests never judges them, since it would share their blind spots.

Nothing checks mechanically that a test can fail, so this review is what judges it. Each test is judged on two questions:

- **Can it fail for a real reason?** It must check what a user can see and do (roles, accessible names, visible text), not internal details, and must not assert something that is always true, such as a constant checked against its own value. A test whose only check is how many times a function or an API was called fails too, unless the count is the behavior, as in a cache or a retry.
- **Is it worth keeping?** It should test your code, not a library's. A parent component's test should cover how its children work together, not repeat what each child's tests already check. A test of formatted output checks your logic (the conversion, the locale chosen), not the exact characters `Intl` produces. A unit test fails this question when a route or story test already checks the same thing, when it proves what the type checker or lint already proves, or when its logic is neither important nor likely to fail. Several tests of one function that could share one table of cases should be one test. When several routes turn an API failure into the same response through one shared helper, one test of that helper's mapping is enough, unless a route maps it differently.

When a component's own code handles keys or moves focus (a menu's arrow keys, or focus moved when a dialog opens or closes or when an error appears), the reviewer also expects its story tests to drive it from the keyboard and check where focus lands. Without that, the verdict is a fix. An accessibility scan of a rendered component tests neither. Native form controls in their normal order get this from the browser and need no keyboard test. The reviewer gives a delete verdict to a test that only checks their tab order, or a `required` attribute set as a plain prop. A `required` attribute your form's schema sets is yours to test.

A flow test is also judged against its flow in the SPEC. The verdict is a fix when the test never checks the flow's outcome (a heading after submit, but never that the save took effect) or, for a web app flow, when its `@covers` line leaves out an app folder the branch changed for the flow. That line is a comment at the top of the test that lists the app folders the flow runs through. The reviewer never asks for a test of an error path nothing stated.

Each test gets a keep, fix, or delete verdict. The reviewer edits no test or source file itself.

### The worthiness step

A plain request, `/gaia-debt`, and a plan without a test-design table each finish this review once the draft pull request is open and before the first audit round. If no changed test needs a verdict, the step ends with no commit.

- **Keep**: nothing more happens. A test that already has a keep for its current content is not reviewed again.
- **Fix**: a fresh sub-agent fixes the test, GAIA commits the fix, and the reviewer judges the changed test once more. If it still gets a fix verdict, or the fixer cannot fix it, it becomes an [accepted residual](/maintenance/residue/#what-a-residual-is). If it now gets a delete verdict, the delete steps below apply. A fix for a test this branch did not change goes to [tech debt](/workflow/tech-debt/) instead.
- **Delete**: Claude shows you the evidence (the redundant assertion and the test that already covers it) and asks you to confirm the delete or keep the test. An approved delete goes to the same fixer. A refused delete keeps the test with no residual. In an unattended run, the test stays and a residual is recorded.

The [Code Audit Team](/workflow/code-audit-team/) runs this step again after each round in which its fixer commits a repair, on the tests that repair added or changed. A fix is made right away, so the next round reviews it, and a delete becomes a residual. If a changed test still reaches the end of the audit without a verdict, such as one committed outside the audit, and it then gets a fix or delete verdict, Claude lists those tests and recommends keeping each as an accepted residual, so the finished audit stands. You can pick tests to repair instead, which costs another audit round and one more CI run. In an unattended run they become residuals.

### What you see at the end

The summary at the end of the work lists what the drift check or the worthiness step decided, such as accepted residuals, deletes you refused, and fixes filed as tech debt.

Before merging, a hook checks that every changed test has a verdict on record for its current content. See [the worthiness verdict gate](/reference/gates/#worthiness-verdict).

## Test-driven development with `/tdd`

Test-driven development (TDD) writes each test before the code that makes it pass. It is opt-in in GAIA, a tool for logic where writing the test first helps, such as a parser or a rule with many edge cases. Type `/tdd` with what to build, or ask Claude to build it test-first:

```
/tdd a parser for the import file's date column
```

Seeing a test fail before the code exists shows it can catch the bug it describes. Writing it first also makes Claude decide how the code will be used before how it works. Martin Fowler covers the practice in [Test Driven Development](https://martinfowler.com/bliki/TestDrivenDevelopment.html).

### The loop

1. **Plan.** Claude picks the layer the test belongs in (see [Where tests go](#where-tests-go)). It names each behavior a user can observe and the one test that covers it, not one test per function. One test can cover several behaviors, and a behavior that already has a test extends that test instead of getting a second. It asks you to approve that plan or revise it. It focuses on the critical paths and the complex logic, not every edge case.
2. **One tracer test.** One test that checks one thing from start to finish, to prove the test setup works before real coverage is added.
3. **One behavior at a time.** For each remaining behavior, one failing test, then only enough code to pass it. Claude never writes all the tests first and all the code after, because tests written in bulk describe how Claude imagines the code will behave, not how it does.
4. **Refactor on green.** Once every test passes, Claude removes duplication from the code this cycle wrote and moves complexity behind simpler interfaces, running the tests after each step.

Before writing the code, Claude runs each new test and checks that it fails for the right reason. It first writes a placeholder with the code's final name and types that returns the wrong value, then writes the test against it, so the test fails because the real code is missing. It never breaks working code to force a failure. When the code already exists, Claude writes the test against it as it is, and the worthiness review judges it like any other.

If a test still won't pass after a few focused attempts, Claude stops and tells you what is blocking it instead of reworking the code until something passes. The test, the interface, or an assumption may be wrong.

At the end, Claude's summary lists each source file it touched, then the worthiness review's verdicts, most severe first, with a count when there are more. A test that could not fail for a real reason is already rewritten in place, and you review it like any other edit. Claude asks you about each proposed delete, showing its evidence.

## Testing another stack

GAIA ships testing references for two stacks.

- **React**: the `tdd-react` skill, for the app in `apps/web/`.
- **Shell**: for the shell scripts your own skills and hooks run, tested with [bats](https://github.com/bats-core/bats-core). Tests go in `tests/shell/`, one file per script, and `pnpm test:shell` runs them. GAIA installs bats as a dev dependency, so there is nothing else to install. The runner refuses to start under a bash older than 4, because bash 3.2 (the default on macOS) lets some failing tests pass. On a Mac, ask Claude to put a newer bash first on your `PATH`. The `bats-assertions` [rule](/reference/rules/#path-scoped-root) loads whenever Claude edits a `.bats` file, so it writes checks that can actually fail. The Tests workflow runs the suites on pull requests that change shell (see [GitHub workflows that ship](/workflow/git-conventions/#github-workflows-that-ship)).

When you add a backend or another package, give Claude the equivalent reference for it:

```text
Add a testing reference for <stack> in <folder>, following the pattern of the tdd-react skill: test layers, where each kind of test lives, what to mock, and good and bad examples. Then point the tdd skill's stack list at it.
```
