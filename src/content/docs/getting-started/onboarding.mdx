---
title: Onboarding, as you build
description: How GAIA onboards a new project as you build. Everything is installed from the start, and rules, commit checks, the pre-merge audit, and the maintenance commands each step in the first time your work reaches them.
---

Everything GAIA installs is on from your first session; nothing needs switching on. Each part steps in the first time your work reaches it. The last few commands appear only once your project has enough history for them.

## First session

- **Rules load.** Some shape everything Claude writes. Others load only when the work touches certain folders or file types. See [Rules](/reference/rules/).
- **Skills start from plain prompts.** Ask for a component and `new-component` scaffolds it. See [Skills](/skills/).
- **Guards are on.** Hooks keep Claude from reading secrets, running dangerous deletes, and committing to `main`, in every permission mode. Claude takes the safe route and carries on. See [Hooks](/reference/hooks/).

## First commit

- **Work happens on its own branch.** By default GAIA does the [work](/workflow/work-lifecycle/) in a git worktree ([why](/reference/gates/#worktree-path-mismatch)). If the work closes an issue, GAIA claims it first ([why](/reference/gates/#issue-claim)).
- **Checks before the commit.** GAIA runs typecheck, lint, unit and end-to-end tests, and a production build, then asks you to approve the commit. See [Quality Gate](/workflow/code-audit-team/#quality-gate).
- **Test seen failing first.** A new test for plain logic must fail before it passes, which proves it can catch a bug ([why](/reference/gates/#test-seen-failing-first-red-gate)).
- **Git hooks.** Pre-commit checks the staged files ([why](/reference/gates/#pre-commit-floor)) and commit-msg checks the message format ([why](/reference/gates/#commit-message-format)). Neither can be skipped ([why](/reference/gates/#no-verify)).

## First pull request

- **Draft and title.** The pull request opens as a draft ([why](/reference/gates/#draft-pull-requests)) with a title in commit-message format, since a squash merge uses it as the commit message ([why](/reference/gates/#pull-request-title)).
- **Code Audit Team.** AI reviewers, each owning certain files, review the change and GAIA fixes what they find until it passes ([why](/reference/gates/#merge-without-the-audit)). See [Code Audit Team](/workflow/code-audit-team/).
- **The branch checkpoint.** If your session's context runs low, or the reviews keep finding new problems, GAIA stops and asks you whether to continue ([why](/reference/gates/#audit-checkpoint)).
- **GAIA-Audit.** When the audit passes, GAIA posts a `GAIA-Audit` status check. After a repo admin runs [`/setup-gaia`](/getting-started/setup-gaia/), GitHub requires it to merge ([why](/reference/gates/#gaia-audit-required-check)).
- **Merge**, when you ask. GAIA shows what the pull request [cost](/models-and-context/cost/).

## First week

- **Tech-debt issues appear.** When Claude spots a problem unrelated to the current work, GAIA files it as a `tech-debt` issue and keeps going. Security findings are never filed publicly. See [Tech debt](/workflow/tech-debt/).
- **Maintenance nudges.** The statusline names maintenance commands, such as `🐛 /gaia-debt` or `📦 /update-deps`, when they are due. See [Nudges](/workflow/statusline/#nudges) and [Maintenance](/maintenance/).

## Later

- **[`/gaia-debt`](/workflow/debt/)** fixes the tech-debt backlog, highest severity first.
- **[`/gaia-residue`](/maintenance/residue/)** appears once 5 or more trade-offs accepted at merge are at least 30 days old.
- **[`/gaia-codify`](/maintenance/codify/)** appears once the audit has made the same kind of finding on 3 or more pull requests in 90 days, and proposes a check that prevents it.

Every check is in the [gate reference](/reference/gates/): what it stops, why, and how to clear it.
