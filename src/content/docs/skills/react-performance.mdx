GAIA includes a render-performance diagnostic, the `gaia-react-perf` skill. You point it at one specific interaction, like a button click, and it finds the component that re-renders when it shouldn't, explains what is causing the extra work, and recommends a fix.

It measures. It does not change your code. You read the diagnosis, then ask Claude to apply the fix in the same conversation.

## How to ask for it

Name the page and the one interaction to measure:

```text
Profile renders when I click the theme toggle in the header on the home page, and tell me which component re-renders when it shouldn't and why.
```

You can also type `/gaia-react-perf <page and interaction>`.

The skill loads only when you clearly ask about rendering, with phrasing like "profile renders", "measure renders", "why is X re-rendering", or "diagnose render performance". It does **not** load for a vague "feels slow", "janky", or "optimize my app". [React Doctor](https://github.com/millionco/react-doctor) covers those.

It needs one small interaction, such as a button click on a specific page. A page navigation or "the whole app" will not work: a navigation re-renders the whole page, and the cause gets lost among hundreds of framework renders. If you don't name an interaction, Claude asks for one.

## What Claude does

Claude writes a temporary [Playwright](https://playwright.dev/) test that performs your interaction in a real browser, records every render it causes, and reduces the recording to a short ranked summary. The raw recording stays on disk, out of your context, and the temporary test is removed when the diagnosis is done. Claude starts the dev server, in the main checkout or a worktree.

<Aside type="caution">
The recording works only on a development build, which is what Claude starts. It cannot record a production build.
</Aside>

## What you get back

A component wrapped in `memo` should skip re-rendering when its inputs have not changed. The diagnostic looks for renders where that memo was defeated: every changed input is a newly created object or function, the same value in a new copy, so React treats it as changed.

Findings are ranked by memo-defeated renders times the slowest render's time. A component is also flagged when it and its children take longer than the frame budget: 16ms, one frame at 60 frames per second. Ask Claude for a different budget if your target differs.

For the top finding, Claude tells you:

- **The component and the count:** how many times it re-rendered during the interaction, and how many of those renders were memo-defeated.
- **The unstable input:** the prop, context value, or piece of state that arrived as a new copy each time.
- **The cost:** whether the component and its children are actually expensive to render, measured against the frame budget.
- **The recommended fix,** from the table below.

## Fixing it

Fix the structure first. If a value never changes, move it out of the component to a constant at the top of the file. A value that depends on render state is memoized for you by the [React Compiler](#under-the-react-compiler). If such a value still arrives as a new copy, the compiler skipped that component (a bailout). Fix the cause of the bailout, or apply one of the exception cases in the [`react-code`](/skills/code/#react-code) skill. Don't add `useMemo` or `useCallback` by hand.

| Unstable input | Structural fix (try first) | When it depends on render state |
|---|---|---|
| An inline object or array prop | Move the literal to a constant at the top of the file | Fix the compiler bailout, or apply an exception case |
| A callback prop | Move the handler to the top of the file when it uses nothing from the component | Fix the compiler bailout, or apply an exception case |
| A context value built on every render | Move a static value to a constant at the top of the file, or split the context so components that don't use the changed part stop re-rendering | Fix the compiler bailout, or apply an exception case |
| A child component defined inside another component's body | Move the component to the top level of the file | Not a memoization fix |

Claude recognizes the last case from the component's name and the unstable input, since the recording does not show where a component is defined.

To apply the fix, ask:

```text
Apply the recommended fix for the top finding, then profile the same interaction again to confirm it is gone.
```

After a real fix, the component disappears from the findings: a memo that works skips its render.

## When to stop

The diagnosis is done when both of these hold for your app's components:

- No render is memo-defeated.
- No render goes over the frame budget.

Claude names any leftover findings as out of scope instead of chasing them: a framework render your app cannot fix, or an app finding far below the frame budget.

## Under the React Compiler

The React Compiler is on by default and memoizes components for you, so the diagnostic counts a compiled component as memoized. A memo-defeated render on a compiled component therefore means its inputs arrive unstable from code the compiler does not compile, such as a third-party component or a file opted out with `"use no memo"`. It does not mean a manual memo is missing.

The fix is still structural first. The compiler memoizes values that depend on render state, so when one still arrives unstable, the compiler skipped that code because it breaks one of the [Rules of React](https://react.dev/reference/rules). Fix the bailout, or apply one of the exception cases in [`react-code`](/skills/code/#react-code). Never wrap everything in memo.

To measure what the compiler itself saves on an interaction, ask:

```text
Measure what the React Compiler saves on <interaction>: profile renders with the compiler off and on, and compare.
```

## When to use it, and when not

Use it to find out why a memo that should skip a render does not, on one concrete interaction.

Keep the cost in perspective. A memo-defeated render of a small component costs about 0.038ms, hundreds of times under the 16ms frame budget. The diagnostic is most valuable when the defeated component is expensive enough to go over the budget. Don't let a finding with no noticeable cost tempt you into wrapping everything in memo.

Two limits:

- **StrictMode doubles timings.** The recording turns it off. If a run leaves it on, Claude says so; compare those timings with each other, not as real durations.
- **App versus framework code is judged by component name.** A component with an unusual name can slip through, so review the fix yourself.
