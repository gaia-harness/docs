GAIA ships ten [sub-agents](https://code.claude.com/docs/en/sub-agents) in `.claude/agents/`. You never start one yourself: a workflow starts each one when it needs it. Each sub-agent starts with a fresh context, so a reviewer judges the work without the reasoning of the session that wrote it, and its reading stays out of your session's context. Each agent uses a [fixed model](/models-and-context/model-choice/) and runs at your session's [`/effort` level](/models-and-context/model-choice/#effort). Each agent can use only the tools listed in its definition, which keeps what it starts with small.

| [`audit-loop-unit`](#audit-loop-unit) | Opus | the merge workflow | Commits fix rounds |

## The Code Audit Team

The audit before each merge is done by a team. Each member is responsible for the files that match its patterns in `.gaia/audit-ci.yml`, and a pull request is reviewed by every member whose files it changes. Members only report problems. A separate fixer makes the repairs, and a scripted check confirms each repair. Every finding is graded Critical, Major, or Minor. See [Code Audit Team](/workflow/code-audit-team/) for the member list, approvals, and the loop.

### code-audit-frontend

The default member. Responsible for every package under `apps/` and `packages/`, which in a new project means the app and its tooling: `apps/web/app/**`, tests, [Storybook](https://storybook.js.org/) and [Playwright](https://playwright.dev/) trees, manifests, build and lint configs, root tooling such as `.npmrc`, and `apps/web/.claude/**`. It reviews what lint and types cannot: security (a top priority), performance, how well the code fits the architecture, edge cases, accessibility, and maintainability. On a package that is not a React app, it skips its React, project-pattern, accessibility, and translation checks and keeps the rest. It also flags slow nested lookups (one loop inside another) that are split across two components or functions, where they are easy to miss. It checks each `eslint-disable` a change adds, too, and flags one where fixing the code would have been better or whose reason does not say why the fix would be worse.

Line-by-line rule checks go to [`audit-rule-specialist`](#audit-rule-specialist) agents, one per area: React patterns and accessibility, [TypeScript](https://www.typescriptlang.org/) and architecture, and translations. Library-specific rules live in `apps/web/.claude/agents/code-audit-frontend/`: `cn`, [Conform](https://conform.guide/), the form components, React buckets, react-i18next, and [shadcn](https://ui.shadcn.com/). It also runs [React Doctor](https://github.com/millionco/react-doctor), [Knip](https://knip.dev/), and a dependency security advisory check, and merges their output into its report in a Tooling table. Those findings are advisory: they never block its approval.

Before it reports a Critical or Major finding, an [`audit-refuter`](#audit-refuter) tries to disprove it. A finding that does not hold up is dropped or downgraded.

If a specialist or refuter cannot start because Claude Code has not loaded its agent type (a session started before an update that added it), `code-audit-frontend` does that review itself and says so in its report. Restart Claude Code to load the new types.

### audit-rule-specialist

Checks changed files against the line-level rules for one area and reports every violation, graded and tagged with a confidence. It starts only when the change has files for its area:

- **React patterns and accessibility**: any changed `.tsx` file.
- **TypeScript and architecture**: any changed `.ts` or `.tsx` file, language files included.
- **Translations**: a changed language file under `apps/web/app/languages/`, or a changed file that calls the translation functions (`useTranslation`, `<Trans`, `i18n.t(`, or `t(`).

It is given the paths of the library rule files for its area and reads each one in full. It edits nothing. Its reply ends with a `Files reviewed` count, so a specialist that stopped early is caught and run again instead of being read as clean.

### audit-refuter

Tries to disprove one Critical or Major finding from `code-audit-frontend`. It reads the flagged line, the code that calls it, and the tests that cover it. It can overturn the finding only with concrete evidence: a guard at a `file:line` that stops the problem, a test that already checks the right behavior, or proof the failing path cannot be reached. Without that, the finding stands. It edits nothing.

### code-audit-github-workflows

Responsible for `.github/workflows/*.yml` and `.github/actions/**/*.yml`. Reviews workflow YAML for script injection, unsafe `pull_request_target` use, unpinned third-party actions, over-broad permissions, and secret handling.

### code-audit-shell

Responsible for every `.sh` and `.bats` file, `.claude/hooks/**`, `.githooks/**`, and the root `.claude/settings.json`. Reviews the shell you write, and your own edits to shell GAIA ships, for unquoted variables, failures that pass silently, guards that allow when they should block, and code that breaks on macOS's bash 3.2 or its versions of `sed` and `date`. For a Claude hook, it also checks that the hook reads its input safely and never breaks your session on its own error. For a bats test, it checks for assertions that can never fail and for tests weakened or skipped without a reason. A change that comes from applying a GAIA update skips GAIA's own shell files. Light review is on for changes up to 30 lines, except Claude hooks, git hooks, bats tests, and `.claude/settings.json`. See [Code Audit Team](/workflow/code-audit-team/#members).

### audit-loop-unit

Runs a batch of audit rounds outside your main session. It runs the branch's [code review](/workflow/code-audit-team/#the-code-review), starts the members, the fixer, and the checker, runs the Quality Gate, commits and pushes each round's fixes, and returns a short report. Your session keeps only that report, so a long audit does not fill its context. It never merges and never posts `GAIA-Audit`; the main session does both. It starts the members as agents of its own, and the members start their specialists and checkers one level below that. This nesting needs Claude Code 2.1.287 or later.

### audit-light-reviewer

Reviews a small change made since a member's last full review, for members that turn this on with `light_review: true` in `.gaia/audit-ci.yml`. `light_line_cap` sets the largest change that qualifies (at most 50 lines), and `light_hard_full` lists patterns that always get a full review. Read-only. Whenever GAIA cannot confirm a change qualifies, the full member runs instead. To turn it on for a member, ask Claude:

```text
Turn on light review for the <member> Code Audit Team member, with a line cap of <n>, and make <paths> always get a full review.
```

It also takes the first review of a small, purely presentational change, before any member has read the branch. A script admits only presentational shapes (static text, swapping one HTML tag for another, static class changes, translation text with the same keys and placeholders, story `args:` values). See [Light review](/workflow/code-audit-team/#light-review).

## Tests

How it fits into testing is described in [Testing](/workflow/testing/).

### worthiness-evaluator

The reviewer for every test the work changed. It always starts in a fresh context, since the session that wrote the tests would share their blind spots. The `tdd` skill starts it once the tests pass, and its verdicts are advice there. The [worthiness step](/workflow/testing/#the-worthiness-step) starts it before the first audit round and acts on its verdicts. It reads only the tests the work changed plus the test files next to them, and reads source code only to judge whether a test goes through the public interface. For a test of one of a SPEC's [critical flows](/workflow/spec/#critical-flows), it also reads that flow in the SPEC, the code the flow runs through, and the route, unit, and real-server tests for that code, only to see which error paths they cover. It gives that test a `fix` when an error path the code has goes untested by the flow test and by every route, unit, and real-server test, when the test never checks the flow's outcome, or, for a web flow, when the test's list of the folders it covers misses one the branch changed for that flow. It edits no test or source file. The only file it writes is its list of verdicts.

It judges each test on honesty and worthiness (see [the worthiness review](/workflow/testing/#the-worthiness-review)) and returns one verdict per test: `keep`, `fix`, or `delete`. Every `fix` or `delete` carries evidence: the defect for a fix, and for a delete the reason, such as the redundant assertion and the test that already covers it. A delete whose cited assertion it cannot find in the sibling file is downgraded, never proposed. Each verdict is recorded, keyed to the test's current content, and the [worthiness verdict](/reference/gates/#worthiness-verdict) gate checks that record at merge.

## Integration health

### overlap-evaluator

Started once by a plan run's [overlap pass](/workflow/testing/#the-overlap-pass), after the worthiness step. It reads the tests the branch changed, the tests that might already cover the same thing on the same or another layer, and source code only to judge whether a claim holds. For each duplicate it proposes to drop it, merge it, move it to another layer, or keep both. It can also propose deleting several tests that one existing route, story, or real-server test already covers. It also proposes moving a browser test that needs no browser to a [real-server test](/workflow/testing/#where-tests-go). It edits no tracked file. The only file it writes is its list of proposals, which a script checks before you approve any of them.

### fitness-judge

The part of [`/gaia-fitness`](/maintenance/fitness/) that makes judgment calls instead of fixed checks: whether descriptions say enough, whether two skills would trigger on the same request, whether a rule's `paths:` patterns fit what it covers, and whether a skill uses its terms consistently. Read-only, and it never changes the grade.
