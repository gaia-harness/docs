`/update-gaia` pulls the latest GAIA release into your project with a [three-way merge](#the-three-way-merge): GAIA's changes come in, your customizations stay, and you answer one question per real conflict. When a new release is available, the statusline shows <Nudge cmd="update-gaia" text="🚀 /update-gaia" />.

It runs like every [maintenance command](/maintenance/#how-maintenance-commands-run): from the main checkout, in a worktree of its own, ending in a pull request.

## How to invoke

Click the <Nudge cmd="update-gaia" text="🚀 /update-gaia" /> statusline indicator, or ask in plain language:

- "update GAIA"
- "pull the latest GAIA"
- "apply the new GAIA release"

## What it does

1. **Checks where it is running** and reads your GAIA version from `.gaia/VERSION`. It never moves you to an older version.
2. **Pulls first if your checkout is behind** the remote's GAIA version, then offers to continue from the pulled copy.
3. **Checks whether a teammate is already updating.** Each run marks itself with a draft pull request (step 7). If a teammate's update is in progress, your run stops and names their pull request; the statusline shows it too. If the open update is your own, the run resumes it or closes it to start fresh.
4. **Downloads and verifies the bundles.** The bundles for your current version and the latest release are checked against their published checksums before anything else happens. On a mismatch nothing has changed: the bad download is deleted and the run stops. Run `/update-gaia` again for a fresh download. If that one still doesn't match, the release is damaged or tampered with; type [`/gaia-forensics`](/maintenance/forensics/) to report it.

   Then it checks this machine's tools against the new release's own list. A tool that is missing or too old stops the run before anything is branched or merged, and Claude walks you through updating it in the same run. See [Tools](/reference/tools/#checked-on-every-setup-and-update).
5. **Picks the migration notes** shipped in the verified bundle (see [Migration notes](#migration-notes)).
6. **Shows the changelog** from your version to the latest, every release in between included, and asks **Proceed** or **Abort**. Abort leaves your project unchanged.
7. **Creates an update worktree** on an `update/v<version>-<timestamp>` branch cut from `main`, leaving your checkout's branch, files, and `node_modules` as they were. It opens the draft pull request that marks the update as in progress, so two teammates never update at once.
8. **Merges every file** ([The three-way merge](#the-three-way-merge)), then asks one question per real conflict, up to four per prompt. Answers are committed in `.gaia/update-decisions.json`, so the next update does not ask again, except about items you put off.
9. **Follows after-merge migration notes** and runs any new project-wide [setup steps](/getting-started/setup-gaia/#8-new-setup-steps-from-later-releases) the release adds.
   - A step that needs a repo admin, such as the [required CI checks](/getting-started/setup-gaia/#recommended-defaults-admin-only), applies only when an admin runs the update; otherwise the summary lists it as owed. From 2.4.0 the update also offers an admin [auto-merge](/getting-started/setup-gaia/#recommended-defaults-admin-only).
   - Setup steps for this machine wait for the merge (step 12), because they act on your main checkout.
   - When a new [Code Audit Team](/workflow/code-audit-team/#the-roster-check) member covers paths you had listed in `unowned:`, those entries are removed and listed in the summary with their new owner. If a removed entry also covered files no member reviews, the summary says so; ask Claude to add a narrower `unowned:` entry for them.
10. **Writes the new version**, runs the Quality Gate, and shows a summary: every file by outcome, every answer, every item still deferred, and any action the release notes say you owe (a dependency GAIA dropped, a file it removed). Nothing is removed for you; ask Claude to carry out any of them. Harness files where your edits were combined with GAIA's are recorded, so the statusline can suggest [`/gaia-fitness`](/maintenance/fitness/#the-statusline-nudge) to review them once the update lands.
11. **Asks once to commit**, then pushes to the draft pull request, whose description becomes the summary. It merges through the [Code Audit Team](/workflow/code-audit-team/).
12. **After the merge.** When Claude merges the update, it offers the [leftover-file cleanup](#leftover-file-cleanup) and runs the new setup steps for this machine. After a merge on github.com, type `/setup-gaia` in your main checkout to run them.

The run ends with a [cost line](/models-and-context/cost/).

**Why the checksum:** a tampered or corrupted bundle would be merged straight into your Claude setup and hooks. See the [gate reference](/reference/gates/#update-gaia-checksum).

`/update-gaia --local <tarball>` merges a bundle built from a GAIA source checkout instead of a release, to test unreleased GAIA changes on a project. Your own project cannot produce that tarball. See [Test an unreleased build in a project](/contributors/release/#test-an-unreleased-build-in-a-project).

## The three-way merge

For every file GAIA ships, `/update-gaia` compares three copies:

- **Yours**: the file in your project now.
- **Base**: the same file in the GAIA release your project is on, the version in `.gaia/VERSION`. If the project was last synced from an unreleased GAIA build (it has a `.gaia/VERSION-dev` file), the base is that build, as long as this machine still keeps a copy of it.
- **Latest**: the same file in the new release.

The base is what makes the merge safe: comparing yours with the base shows what you changed, and comparing the latest with the base shows what GAIA changed, so the merge never guesses whose edit a difference is.

| What changed since the base | What happens |
| --- | --- |
| Only you changed the file, or nobody did | Yours stays as it is. |
| Only GAIA changed it | GAIA's new version replaces yours. |
| You both changed it | The two sets of changes are merged, then checked by Claude (below). |
| The file is new in the release | It is added. |
| You deleted the file | It stays deleted. |
| GAIA removed the file, and you never edited it | It is deleted. |
| GAIA removed the file, and you edited it | You are asked whether to remove it or keep it. |

When you both changed a file, `git merge-file` merges the two line by line, then Claude reads both changes side by side, even when the text merged cleanly. Two edits can solve the same problem on different lines and merge into duplicate or contradictory instructions, which a line-by-line merge cannot see.

- **Separate concerns that merged cleanly** are written with no question.
- **Everything else** becomes one question: a text conflict, two changes to the same thing, or changes that contradict each other. The answers are **Combine** (both changes in one version, shown to you first), **Keep mine**, **Take GAIA's**, and **Decide later**, with the recommended one first. When your change covers something GAIA's misses, Claude suggests opening an issue on [gaia-harness/gaia](https://github.com/gaia-harness/gaia) describing it.

Every file the merge overwrites or deletes is backed up first, under `.gaia-backup/<timestamp>/` in the update worktree (gitignored).

### How GAIA classes its files

`.gaia/manifest.json` is GAIA's list of the files it ships. It gives each file one of three classes, which decide the recommended answer when you and GAIA both changed it:

- **`owned`**: GAIA maintains the file. Most of `.claude/`, `.gaia/` and `.githooks/` is owned. A conflict question recommends GAIA's version. If you already had a file of your own at a path a new release starts shipping, yours is backed up and replaced.
- **`shared`**: GAIA ships a starting version you are expected to customize, such as `CLAUDE.md`, `.claude/settings.json`, `package.json`, `.gaia/audit-ci.yml`, `apps/web/app/styles/theme.css` and the CI workflows. A conflict question recommends keeping yours. If you already had a file at a path a new release starts shipping, you are asked instead of overwritten. When the update writes `.claude/settings.json` from one of your answers, Claude Code asks you to approve the write, because [GAIA guards that file](/reference/gates/#claude-settings-file). Approve it if it matches your answer.
- **`wiki-owned`**: pages in `wiki/` that GAIA ships. They merge like `shared` files, and sections you added to one are kept.

### What the merge never touches

- **Files GAIA does not ship.** Anything not listed in `.gaia/manifest.json` is yours.
- **`wiki/log.md`, `.gaia/VERSION`, `.gaia/VERSION-dev`, `.gaia/manifest.json` and `.gaia/update-decisions.json`.** The update writes the last three itself. A local sync writes `.gaia/VERSION-dev`, and the next release update removes it.
- **`.gaia/packages.json`**, the list of packages in your workspace. It is yours from the start.
- **`.gaia/finding-classes.json`**, your project's own [audit finding classes](/maintenance/codify/#your-own-finding-classes). It ships empty and is yours from the start.
- **Your design system, once it is established.** After you settle your project's design (the `Design System` wiki page is marked established), that page and `apps/web/.claude/rules/design-baseline.md` become yours, and later updates skip both.
- **`apps/web/.claude/settings.json`.** It is never merged. GAIA rebuilds it from the root `.claude/settings.json` plus `apps/web/.claude/settings.overlay.json`, so put frontend-only settings in the overlay.

`package.json`, `pnpm-workspace.yaml` and `.gaia/audit-ci.yml` are merged key by key. A key only you added, or one you removed, is never touched. A key GAIA changed that you left alone takes GAIA's value. A key you both changed becomes a question. Your dependencies, overrides, build approvals and [Code Audit Team](/workflow/code-audit-team/) entries stay as you set them.

The one exception is a package GAIA renames (in 2.2.0, `@gaia-react/lint` to `@gaia-harness/lint`): once the new name lands in your `package.json`, the old one is deleted from the same section, even if you changed its version.

After the merge, GAIA rebuilds each Code Audit Team member's list of covered files from your `.gaia/audit-ci.yml`, so it matches your project, not GAIA's.

## Leftover-file cleanup

GAIA keeps machine-local state under `.gaia/local/`, which is never committed. When a release retires a feature, the cleanup deletes the files that feature kept there. Files it doesn't recognize are listed, never deleted.

The cleanup runs after the merge, in your main checkout, because it needs the new release there. When Claude merges the update, it pulls your main checkout, lists the leftover files, and asks before deleting them. It then refreshes the [React Doctor](https://github.com/millionco/react-doctor) skill, if this machine has it, and runs the setup steps for this machine that the update held back.

If you merged on github.com, or the pull failed, start Claude in your pulled main checkout (not a worktree) and ask:

```text
The GAIA update merged. Run GAIA's leftover-file cleanup from this main checkout, show me the list, then apply it if I agree.
```

Then type `/setup-gaia` there to run the held-back setup steps for this machine.

Every machine has its own `.gaia/local/`. A teammate who runs `/update-gaia` after the update merged gets the pull (step 2), their machine's setup steps, and the cleanup offered. A teammate who pulled some other way can paste the same prompt.

## Stopping and resuming

A stop after the update worktree exists leaves it in place, changes nothing in your main checkout, and prints the worktree's path. Re-run `/update-gaia` to resume: before the version write, it safely repeats the merge with your answers; after it, re-run inside the update worktree and it picks up at the Quality Gate.

To throw the stopped update away instead, ask Claude:

```text
Discard the stopped GAIA update: close its draft pull request, then remove its worktree and branch.
```

## Migration notes

A release can ship migration notes, `.gaia/migrations/<version>.md`, for steps a file merge cannot do: moving a directory tree, rewriting a config, removing a retired feature. `/update-gaia` reads them only from the verified bundle and follows the notes for every version between yours and the latest, oldest first.

- **After-merge** notes run after the merge and before the version write. They are safe to repeat.
- **Blocking** notes stop the update before anything is branched or merged. `/update-gaia` names the note and asks whether to follow it now. Following the note brings you to that note's version; re-run `/update-gaia` afterwards to get anything newer.

## Gotchas

- An update to the same version that is already applied but not committed is reported as such, never as "up to date". Commit it, or start over by asking Claude:

  ```text
  Discard the uncommitted GAIA version change so I can run /update-gaia again.
  ```
